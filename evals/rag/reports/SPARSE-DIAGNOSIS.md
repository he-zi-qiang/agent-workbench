# 为什么 hybrid 输给 dense：查到一半的诊断

状态：**未定论**。这里记录的是实测现象和被排除的解释，不是结论。

## 现象：sparse 编码跨进程不可复现

同一个查询，三次独立运行，编出的词项数不同：

| 查询 | 运行 A | 运行 B | 运行 C |
|---|---|---|---|
| `RRF` | 0 | 2 | 0 |
| `reciprocal rank fusion` | — | 0 | 1 |
| `AWB-4471` | 4 | — | 3 |
| `Qrdant` | 0 | — | 2 |

**每次运行内部完全自洽**：同进程内连编三次结果相同，批量路径与单条路径也一致。
所以不是随机性，是跨进程状态差异。

## sparse 单独检索：即使编出词项，排序也不对

运行 A 里绕开融合、只用 sparse 查询：

```
'AWB-4471'                                    4 词项 -> [quoted-guarantee, events, error-codes]
'never be reassigned, reordered, or skipped' 10 词项 -> [quoted-guarantee, outbox, authorization]  ✓
'Qrdant' / 'RRF' / 'recieved chunk batch'     0 词项 -> []
```

`AWB-4471` 编出了词项，却把唯一含该错误码的文档排在第 3。

## 已排除的解释

- **不是「短查询固有编不出词项」**：`Qrdant` 在运行 C 编出 2 个词项。
- **不是批量路径 bug**：批量与单条一致。
- **不是随机性**：同进程内可完全复现。
- **不是融合权重**：sparse 单独检索本身就排不对。

## float16 / MPS 假设：已实测排除

先前的猜测是 float16 与 MPS 后端的舍入差异，让阈值边缘的词项在不同进程落到两侧。

**固定 `device="cpu"`、`use_fp16=False`（纯 float32、同一 torch 2.13.0）后，两个独立
进程仍然不同**，而且差异更大：

| 查询 | 进程 1 | 进程 2 |
|---|---|---|
| `RRF` | 2 项 `(627, 54612)` | 1 项 `(54612,)` |
| `Qrdant` | 3 项 `(42, 2396, 58349)` | 1 项 `(58349,)` |
| `recieved chunk batch` | 7 项 `(13, 92, 206, …)` | 1 项 `(24862,)` |
| `AWB-4471` | 0 项 | 0 项 |

假设不成立：精度与设备都不是变量。

## 新线索：疑似权重未完整加载

进程 2 里几乎每条查询都塌成 **1 个词项**，且 `recieved chunk batch` 的那个索引
（24862）**不在**进程 1 的 7 个之内。这不像舍入误差在阈值附近抖动——抖动会让边缘词项
增减，不会让结果整体塌缩并换成一个全新的词。

更像**两次加载得到了不同的模型状态**。旁证：加载时打印
`Loading weights: 0/391 → 391/391`，速度 80000+ it/s，快得不真实。

### 下一步的具体检查项

1. 比较两次加载后 sparse 线性头（`sparse_linear`）的权重张量是否逐值相同；
2. 确认 FlagEmbedding 是否真的加载了 `sparse_linear.pt`，还是回退到随机初始化——
   BGE-M3 的稀疏头是**独立于主干**的一组权重，主干加载成功不代表它也加载了；
3. 若确为随机初始化，则此前所有 sparse 数字（含 #46 的负结果）全部作废。

**在这三项完成之前，任何关于「sparse 有没有用」的结论都不成立，包括 #46 那个
hybrid 劣于 dense 的负结果。**

## 一条已合并的测试是不稳定的

`test_the_real_model_weights_real_terms` 断言 `reciprocal rank fusion` 的词项数
`> 0`，而实测该查询在不同运行里得到 0 和 1。**它一直在通过，是运气**。

没有改动它：在编码稳定之前，把它改成任何具体期望值都是把噪声固化成契约。这条记录
本身就是它的说明。

## 这一轮里没有做的事

**没有把任何单次观察写成测试。** 第一版诊断（"短查询固有地编出零词项"）就是从一次
运行读出的性质，写测试时立刻被下一次运行推翻——那两条测试已撤回。

---

# 结案：2026-07-28

根因是 **BGE-M3 的词法投影头 `sparse_linear.pt` 从未被加载**。它与基座权重分开存放
（3516 字节的独立文件），HuggingFace 缓存里没有它，而 `FlagEmbedding.BGEM3FlagModel`
在它缺失时不报错——构造一个新的 `Linear(1024, 1)` 随机初始化后照常运行。

## 为什么没有任何东西发现它

链上每一环都「成功」：模型加载成功；输出维度 250002 正确（该维度来自 tokenizer
词表，与这个投影无关，所以 `BgeM3SparseEncoder.load` 的维度守卫必然通过，
ADR-013 记录的那条唯一判别性断言也必然通过）；编码返回合法的稀疏向量。

**唯一错的是那些数值是随机的**，而随机性不产生任何错误。

`Loading weights: 391/391 [00:00, 65168 it/s]` 也不是在读盘——它在遍历基座模型的
391 个张量，那个缺失的文件根本不在这个循环里。

## 三条证据

1. **分布**：`sparse_linear.weight` 的 std = 0.01748；`Linear(1024,1)` 的 PyTorch
   默认初始化 `U(±1/√1024)` 理论 std = 0.01804，差 3%。范数 0.559 = √1024 × 0.01748，
   完全吻合。与「刚初始化」无法区分。
2. **跨进程**：两个进程加载同一 model_id + revision，权重 SHA 完全不同
   （`18d1b07c…` vs `4aa7382b…`）。磁盘上的权重不会变。
3. **修复后**：下载该文件，两轮评测的质量指标逐位相同。

## 它解释了此前每一个现象，包括两条被「推翻」的诊断

| 现象 | 真实原因 |
|---|---|
| 短查询编码为空 | 随机投影 + ReLU 有时把全部输出截成零。**这条诊断不是错的，是随机的** |
| float16/MPS 舍入 | 排除得对，但排除后差异仍在——因为真正的原因一直是别的 |
| 跨进程检索结果不同 | 每次是不同的随机投影矩阵 |
| 延迟 184 ms ↔ 33 529 ms | 随机向量的稠密程度随机 |
| hybrid 时好时坏 | 随机投影偶尔碰巧有用 |

## 修复

两半，缺一不可：

1. **取回权重**（3516 字节）——解决本机；
2. **加载器在该文件不在缓存时拒绝启动**——解决所有机器，并在错误信息里给出取回命令。

第二半才是修复的主体。第一半只是让这台机器能继续工作。

## 留下的守卫

`tests/ingestion/test_bge_sparse.py` 新增两条，修复前必失败：

- `test_two_loads_of_one_revision_encode_a_query_identically` —— 契约层面：
  一个被钉住的 revision 必须意味着一个编码器，而不是一族编码器；
- `test_the_lexical_projection_is_loaded_rather_than_initialised` —— 直接命名原因：
  一个新构造的 `Linear` 做不到两次给出相同的数。

两条都需要真权重，CI 会跳过并说明原因。

## 未解决

hybrid 延迟仍在 7–28 秒量级且轮间波动。**与本问题无关**：质量已稳定，延迟仍不稳，
说明它是另一件事。下一步是把稀疏编码与向量检索分开计时——在那之前不给它原因。
