# dense vs hybrid：2026-07-27 的消融，以及它不能回答的问题

| 指标 | dense | hybrid | 差 |
|---|---|---|---|
| recall@1 | 0.957 | 0.957 | 0 |
| recall@3 | 1.000 | 1.000 | 0 |
| MRR | 0.971 | 0.971 | 0 |
| 中位检索延迟 | 52.7 ms | 38136.2 ms | ×724 |

同一份语料、同一份 gold set（digest `f43571b25a871121`）、同样 23 题，只换检索器。
两个 arm 各自独立 collection——sparse 改变 index identity，共用会让 dense 读到为
hybrid 建的点。

## 结论：测不出差别，且这份语料不足以支撑任何结论

三个质量指标**逐位相同**，说明 hybrid 返回的排序与 dense 逐题一致。

这**不**等于「sparse 没用」。这份语料只有 6 篇文档、每篇 1 个 chunk，问题措辞与原文
高度重合；dense 基线已经是 23 题错 1，**留给 sparse 的提升空间只有那一题**。

持平在这里有两种同样成立的解释：

1. sparse 在这类语料上确实无增益；
2. 语料太小、太"顺"，测不出差别。

**这两者用现有数据区分不了。** 把持平写成「hybrid 不值得做」，是拿一个测不出差别的
实验去支撑一个关于方案的结论——这份报告存在的意义之一就是拦住那句话。

## 那个 38 秒不是 hybrid 的固有代价

延迟差了 724 倍，但它衡量的是**当前实现**，不是方案：每次查询都重新跑一遍 BGE-M3 的
稀疏编码，CPU 上没有预热、没有批处理、没有常驻。架构基线 8.1 明确要求
"Embedding 和 reranker 常驻加载、批处理、预热并设置并发/超时"——**这些我都没做**。

所以这个数字可以用来说"当前实现不可用于交互式查询"，不能用来说"hybrid 太慢"。

## 要让下一次消融真能回答问题，语料需要什么

现在这份语料里，没有任何一处是 dense 会漏而 sparse 能命中的：

- **罕见标识符**（错误码、配置键、函数名）——dense 没见过就没有邻域；
- **精确短语**与引号内的原文；
- **错别字或形近词**——term 匹配能命中，语义嵌入会漂走；
- **缩写与全称并存**（RRF / reciprocal rank fusion）。

在补进这些之前，dense 与 hybrid 的对比只会继续持平，而那个持平仍然什么都不说明。
