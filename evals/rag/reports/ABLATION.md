# dense vs hybrid：2026-07-28，修复 sparse 权重之后

## 先说作废的部分

**此前所有 hybrid 数字均无效**，包括本文件前两版记录的两组。原因不是测得不准，
而是被测的东西不存在：BGE-M3 的词法投影头 `sparse_linear.pt` 从未被加载，
每次运行使用的是一个**随机初始化**的投影矩阵。详见 `SPARSE-DIAGNOSIS.md`。

修复后重测，结论与作废的那些相反。

## 结果

两轮独立运行，同一份语料（10 篇）与 gold set（38 题，digest `a26070043b0ffde1`）。

| 指标 | dense run1 | dense run2 | hybrid run1 | hybrid run2 |
|---|---|---|---|---|
| recall@1 | 0.9474 | 0.9474 | **1.0000** | **1.0000** |
| recall@3 | 0.9737 | 0.9737 | **1.0000** | **1.0000** |
| MRR | 0.9605 | 0.9605 | **1.0000** | **1.0000** |
| 检索延迟 | 41 ms | 46 ms | 27 892 ms | 7 219 ms |

**两个 arm 的质量指标都逐位复现。** dense 一直是稳定的，它在这里的作用是对照组：
它证明评测装置（语料、切分、索引、gold、打分）本身确定，两轮之间没有别的东西在变。
hybrid 从「每轮都不同」变成「两轮完全相同」，这是修复生效的直接证据。

## hybrid 优于 dense

38 题全部命中且全部排第一。dense 漏掉 2 题的 rank-1（recall@1 0.947），
其中 1 题连 top-3 都没进（recall@3 0.974）。

这是**第一次可以真正做这个比较**——此前每一次比较都有一侧是随机量。

需要克制的地方：38 题上的 1.000 不是「hybrid 完美」，而是「这个 gold set 不够难，
已经区分不出 hybrid 内部的好坏了」。它能区分 hybrid 与 dense，不能再往上区分。
下一步若要继续测 hybrid，需要更难的问题，而不是更多同类问题。

## 延迟：现象仍在，原因未分离

hybrid 延迟在 7.2 秒到 27.9 秒之间，比 dense 高两到三个数量级，且两轮之间差 3.9 倍。

**本文不给这个现象一个原因。** `retrieval_latency_ms` 把稀疏编码与向量检索合并计时，
所以现有数据分不开至少三种可能：BGE-M3 稀疏编码在本机 CPU/MPS 上本就昂贵、
Qdrant 稀疏检索本身慢、或还有第三个未发现的问题。

不写结论是刻意的。本文件上一版就是把整个延迟数量级归因给一个刚找到的 bug
（融合前截断），而那个归因后来被证明不完整——找到一个能解释现象的原因，
不等于找到了全部原因。

值得记下的是：**延迟仍在波动，质量已经不波动了。** 这两件事此前是绑在一起的
（随机投影同时破坏两者），现在分开了，说明延迟波动不再意味着向量在变。

下一步是把编码与检索分开计时。在那之前，「hybrid 慢」只是一个观测。

## 更正两处旧论断

1. **「hybrid 劣于 dense」**（07-27 版）——建立在随机投影的单次采样上。作废。
   修复后结论相反。

2. **「30.3 秒由融合前截断造成」**——截断确实是一个真 bug，修它是对的；但把整个
   数量级归因给它是过早收敛。修复就位后 33.5 秒重新出现过，说明底下还压着别的。

## 三臂消融（WP05-08）的状态

`scripts/run_rag_eval.py` 已支持第三臂 `hybrid-rerank`，本轮**未跑**：
bge-reranker-v2-m3 的权重（约 2.3 GB）不在本机，两轮运行均设 `HF_HUB_OFFLINE=1`，
脚本按设计跳过该臂并打印原因，不会产出缺一条臂的三臂报告。

现在跑它是有意义的——基线已经可复现。但 hybrid 在这个 gold set 上已经打满 1.000，
**rerank delta 在这里必然为 0**，测不出任何东西。要测 rerank，先要更难的 gold set。

# 跨文档：2026-08-10，49 篇语料与 14 道多跳题

## 结论先写：hybrid 每个单命中指标都赢，唯独"答案到齐"输

单路径（`--paths reference`，生产路径），gold digest `55ec24c7d2b86062`，
52 题 = 38 道单文档 + 14 道跨文档，语料 49 篇，`TOP_K = 3`。

| 指标 | dense | hybrid |
|---|---|---|
| recall@1 | 0.7885 | **0.8846** |
| recall@3 | 0.9423 | **0.9615** |
| MRR | 0.8558 | **0.9199** |
| **full_coverage@3** | **0.8462** | 0.8269 |
| 检索延迟 | 47.8 ms | 21 193 ms |

**hybrid 在三个单命中指标上全面优于 dense，在 `full_coverage@3` 上却更差。**
这不是噪声：两个数字来自同一次运行、同一个索引、同一份金集。

## 那 7 道题

`full_coverage@3` 与 `recall@3` 的差值可以精确归因，因为单文档题的
`coverage_rank` 恒等于 `rank`（见 `metrics.py`）——单文档题不可能"部分命中"。
所以「coverage 失败数 − recall 失败数」就是**捞回了一半答案**的题数：

| 臂 | recall@3 未命中 | coverage@3 未达成 | **只捞回一半** |
|---|---|---|---|
| dense | 3 | 8 | **5** |
| hybrid | 2 | 9 | **7** |

**hybrid 在 14 道跨文档题里有一半（7 道）只返回了半个答案。** 它找到了带有
题面词的那篇，没找到只能靠桥接实体到达的那篇。

## 机制：一个假设，尚未验证

合理的解释是：sparse 按词面重叠计分，会把 top-3 的三个位置都推向"含题面词"
的那一类文档，于是把桥接文档挤出去；dense 是语义的，反而散得开一点。

**本文不把这个当作结论。** 要证实它需要逐题看两臂各自返回了哪三个 chunk，
而报告只写聚合分数。这项归因属于 ADR-037 的前置工作，不属于这份基线。

## 上一版金集为什么作废

同日更早的一版跨文档题（digest `8dfde7bc760839d1`，未提交）测得
`full_coverage@3` 与 `recall@3` **完全相等**（都是 0.9808），缺口为零。
原因是两条，都在出题和语料上：

1. **题目是"拼接"不是多跳**：每道题同时点名了两个文档各自的关键词，两半
   都能被独立检索到，模型不需要"先读 A 才知道 B 相关"。
2. **语料只有 10 篇**，每篇约等于 1 个 chunk，`top-3` 就是**整个语料的 30%**。
   在这个尺度上任何检索器都接近饱和。

现在的 49 篇里，top-3 是 6%，且加入了**只共享表面词、不含桥接实体**的干扰
文档（`policy-oncall` 谈 rotation 但不点名团队，`policy-retention` 谈保留期
但不点名存储）。跑前的静态自检显示 8/14 的答案文档落在 ≥3 个竞争者的人群里；
另外 6 道题面本身就唯一锁定了答案文档，偏易——**没有继续按代理指标调题**，
那等于把金集拟合到出题人的假设上。

## 延迟这次不作数

hybrid 中位 21.2 秒，落在此前记录的 7.2–27.9 秒区间内但偏高。整场会话中这台
机器一直处于内存压力下（一度 swap 14.28/15.36 GB），**这个数字是机器状态的
测量，不是检索器的测量**。质量指标不受影响：它们不读时钟。

## 这解锁了什么

ADR-037 图谱臂的前置条件是"当前实现在跨文档题上有可测量的失败"。**它有**：
生产路径上一半的跨文档题只返回半个答案，而且更强的词面匹配让这件事更糟——
这正说明该加的是能沿实体跳转的臂，而不是更强的 lexical 臂。

# 逐题归因：那 7 道题漏掉的到底是什么（2026-08-10）

`--dump-outcomes` 写出的 `hybrid-reference-outcomes.json`。7 道只返回半个答案的
题形状**完全一致**：

| | |
|---|---|
| doc A（带查询表面词的那篇） | **每次都在第 1 位命中** |
| 缺的 | **永远是桥接目标**（team-kestrel、team-marlin、store-aw-vectors…） |
| top-3 剩下两位 | 被**和 doc A 词汇相近的文档**占满 |

例：问"Ingestion Worker 写入的存储保留多久"，命中 `component-ingestion-worker`，
挤进来的是 `slo-ingestion` 与 `runbook-index-rebuild`，而答案所在的
`store-aw-vectors` 没进；问"AWB-52xx 那个组件的值班频道"，命中
`component-retrieval-service`，挤进来的是另外两个 `component-*`，而 `team-kestrel`
没进。

## 这确认了机制假设，也推翻了修法

机制假设（两条臂都按与查询的表面/语义相似度排序，而查询只描述了 doc A，
于是三个位置全给了 A 的近邻）**成立**。

但桥接实体在哪里，是此前没测过的：

| | |
|---|---|
| **查询**里含桥接实体名字 | **0 / 7** |
| **已命中的 doc A** 里含桥接实体名字 | **7 / 7** |

查询里没有 `Kestrel`、`Marlin`、`aw-vectors`——它描述 doc A 的特征，问的是
doc A 指向的那个东西的属性。所以 ADR-037 §2.1 原本画的
"查询 →实体名 → mention → chunk" 那条臂**一道题也修不了**，
关系臂按"提名边被读出来的那个 chunk"实现同样打偏（那个 chunk 就是 doc A）。

正确形状见 ADR-037 §2.7：**从 dense/sparse 的 top-N 做种子扩展**——反查种子提到
的实体，提名该实体的**其它** mention。融合仍只有一次：种子用于提名候选，不是
第二次融合。

## 为什么这一环值得先收

不收它，B3 会照着 §2.1 把两条臂建出来，跑完消融发现一点没涨，然后从头查起。
一次 20 分钟的评测换掉了那条路。

## 顺带更正一个数量级：hybrid 不慢两三个数量级，慢约 3.5 倍

同一份代码、同一份金集，机器空闲时重跑：

| 臂 | 空闲机器 | 此前那次（swap 压力下） |
|---|---|---|
| dense | 48.2 ms | 47.7 ms |
| hybrid | **171.9 ms** | 21 192.7 ms |

**123 倍的差别全部来自机器状态**：那一轮跑的时候本机 swap 被顶到 7-14 GB，
BGE 权重被反复页入页出。质量指标两轮**逐位相同**（0.8462 / 0.8558 / 0.7885 /
0.9423 与 0.8269 / 0.9199 / 0.8846 / 0.9615），只有延迟行变——这既是本次的
可复现性证据，也说明质量指标确实不读时钟。

此前 `ABLATION.md` 里"hybrid 延迟比 dense 高两到三个数量级"那句话（2026-07-28）
在当时的机器状态下是真实观测，但**不是这个检索器的属性**。真实代价是约 3.5 倍，
主要来自 BGE-M3 的稀疏编码。
