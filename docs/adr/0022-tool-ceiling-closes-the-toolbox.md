# ADR-022：工具额度用尽是收走工具，不是结束这一轮

- 决策点：`max_tool_calls` 用尽时 run 应该怎么办；`max_tool_calls < max_steps` 是不是配置错误
- 状态：**接受**
- 日期：2026-08-07
- 影响：`RunBudget` 去掉跨字段校验；`ClaudeLikeAgentRuntime._run_loop` 每轮重算 `specs`；
  `RuntimeSettings` 去掉同名校验；`config_schema_version` 1.5 → 1.6

## 背景

ADR-021 给 Chat 兜底分支加了 `web_search`，提示词里写着"最多搜两次"。实测两轮，两轮都
以 `budget_exceeded` 收场，而且**两次的原因不一样**：

| 预算 | 发生了什么 | 死在哪 |
|---|---|---|
| `max_steps=6, max_tool_calls=6` | 模型把同一个问题换了五种说法反复搜，每次约 14 秒 | `max_steps`，一个字没写 |
| `max_steps=3, max_tool_calls=3` | 搜了两次、拿到 5.5KB 结果，第三步提出第三次搜索 | `max_steps`，仍然一个字没写 |

第二行才是真问题。**两次搜索都成功了**，结果就在上下文里，模型只差一轮把它写出来，而 run
在那一轮到来之前就死了。交付给用户的是"我没有联网获取最新数据的能力"——一句在事实上就
是错的话。

为什么第二行调不好？因为当时有一条跨字段校验：

```
max_tool_calls >= max_steps
```

在它之下，**工具上限永远不可能先于步数上限触发**。一轮调一次工具时两者同一轮到顶，而
`stop_reason_for` 先返回 `max_steps`。也就是说"最多两次搜索 + 一轮作答"这句话，
在类型系统层面就是**写不出来**的。

## 决策

### 一、工具额度用尽 → 收走工具，让模型作答

循环顶部原本问 `stop_reason_for`（"我还能开始新工作吗？"），任何一条到顶都 `_failed`。
现在改问 `halt_reason_for`（"这个 run 还有事可做吗？"）：

- **步数、token、成本、deadline** —— 到顶就是没事可做了，结束 run；
- **工具调用** —— 到顶只说明**工具不能再调**，模型仍然有一件事可做：**把已经拿到的东西
  写出来**。

于是 `specs` 改为每轮重算：额度还在就照常广告工具，额度没了就传 `()`。

**关键是"拿掉"而不是"留着然后拒绝"**。留着的话，模型看得见 `web_search` 就会提
`web_search`，而对这个提案唯一能做的事就是拒绝它并杀掉 run——那个 run 正握着这次提案本想
改进的结果。把工具拿掉，问的才是这个 run 真正答得上来的问题："用你手上的东西写。"

循环仍然有界，且**边界就是 `max_steps`**：每轮花掉一步，所以关掉工具箱之后不可能空转。

### 二、`max_tool_calls < max_steps` 是**合法预算**，校验删除

旧校验的读法是"一个调不了工具的 step 是配置错误"。在"工具用尽即结束 run"的循环下这个读法
成立；循环改了之后它正好反过来——**那个 step 就是作答轮**。

所以 `RunBudget` 和 `RuntimeSettings` 的同名校验一起删除。删掉之后，
`max_steps=3, max_tool_calls=2` 才第一次能表达 ADR-021 提示词里那句话。

不是加一个可选开关绕过去：项目规矩是突破配置层硬边界要走 ADR + schema 升版，这里照做
（1.5 → 1.6）。

### 三、模型不肯作答时照旧失败

工具拿掉之后模型**仍然**提出调用（有的模型会），那个提案还是被 `_terminal_for_turn` 拒绝、
run 还是失败。这不放宽：一个给了机会还不肯写的 run，失败是诚实的结果。Chat 兜底分支另有
ADR-021 的降级兜着，不会因此 502。

## 后果

- Task 图也受益：`max_steps=12, max_tool_calls=32` 且并行读的 run，此前工具先用尽就整轮
  失败，现在会拿着结果作答；
- **两条 run 的账变了**：工具额度用尽的 run 现在多花一步（那一步就是作答）。
  `test_the_tool_call_ceiling_stops_a_model_that_will_not_take_the_hint` 的
  `steps` 从 2 变 3，是这个改动的直接后果，不是回归；
- `stop_reason == "max_tool_calls"` 变罕见：只有模型在无工具的一轮里仍然提调用才会出现；
- 预算校验从"两条上限互相约束"变成"两条独立上限"。误配的空间因此变大了一点——
  `max_tool_calls` 写成 1 的 Task run 只会调一次工具就转入作答，且**不报错**。
  这是代价，接受它的理由是：反过来的错（把能答的 run 杀掉）已经实测发生过，而且看不出来。

## 备选方案

**只改 Chat 兜底分支，不动 runtime。** 已经做了（ADR-021 的降级），它把 502 变成了回答，
但那个回答来自模型记忆而不是刚搜到的结果——5.5KB 白花。被否决为"不够"，不是"错"。

**把工具留在请求里，只在派发时拒绝。** 就是改之前的行为，实测产物见上表第二行。

**保留校验，把兜底预算写成 `max_steps=4, max_tool_calls=4`。** 算过：模型会搜三次而不是
两次，提示词和预算继续对不上。

**让运行时把失败 run 的 transcript 交给调用方，由 Chat 自己重跑一轮。** 更大的改动，
而且把"怎么收尾一个 run"的知识泄到应用层；收走工具是在正确的层解决同一件事。
