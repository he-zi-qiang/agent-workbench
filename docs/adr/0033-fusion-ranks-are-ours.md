# ADR-033：融合仍然只发生一次，但那一次归我们做

- 决策点：混合检索的结果为什么跨重建索引不可复现；`_ranked` 的并列定序为什么修不好它；
  RRF 的臂内名次该由谁决定
- 状态：**接受**
- 日期：2026-08-10
- 影响：`QdrantVectorIndex.search_hybrid` 从"一次带两个 prefetch 的服务端 RRF"换成
  "两次并发的单臂查询 + 适配器里的一次 RRF"。融合次数不变，仍是一次。
  `VectorIndexPort` 的签名、`ScoredChunk`、分数量纲、两臂各自的 limit 语义**均不变**。
  取代 [ADR-016](./0016-self-built-retrieval.md) 中"融合只在 Qdrant Query API 里发生
  一次"这一条，以及 `ports/vector_index.py` 里 `SPARSE_VECTOR_NAME` 旁边那段注释
- 依赖：ADR-013（sparse 来自 FlagEmbedding）、ADR-016、ADR-017（这条是它第 3 步的堵点）

## 1. 背景：诊断错了，所以药没治病

`_ranked` 的 docstring 把现象写对了——"Qdrant 按分数排序，对分数相等的点不作承诺"——
并据此在适配器里按 `(-score, chunk_id)` 重排。**对 dense 路径这是对的且有效的**：本机
实测 10 次重建索引，dense 每次都给出同一个次序。

对 hybrid 无效，而且无效得不明显。同一份 fixture（5 个共享向量的并列点 + 1 个严格最优的
`chk_zenith`），10 次重建索引测到的是：

```text
round 2   hybrid  zenith:1.000000 pear:0.583333 mango:0.533333 apple:0.392857 ...
round 6   hybrid  mango:0.666667 zenith:0.642857 apple:0.583333 pear:0.533333 ...
round 8   hybrid  cherry:0.666667 zenith:0.642857 apple:0.583333 banana:0.533333 ...
```

**10 次得到 10 个不同的次序，`zenith` 的分数在 0.643 / 0.667 / 0.700 / 0.833 / 1.000
之间跳，并且有 2 次它根本不在第一位。** 它是 cosine 1.0 对 0.9998 的严格最优点。

原因不是"并列分数的次序没定"，是**分数本身就是随机的**。Qdrant 的 RRF 按臂内名次计分，
实测公式是 `Σ 1/(2 + rank)`（rank 从 0 起，用上面 9 个不同分数逐一验算吻合）。一个点在
dense 臂里并列、在 sparse 臂里也并列时，它拿到的名次是引擎内部的任意选择，于是融合分数
是任意的。**排序发生在分数之后，而错误发生在分数之前**——任何后排序都够不着它。

这解释了一个此前记反了的观察。`bootstrap/settings.py` 里 `LlamaIndexSettings.enabled`
保持 `False` 的理由写的是"并列的融合分数从 Qdrant 回来时次序不稳"。次序不稳是结果，
分数不稳才是原因；按前者去修，修出来的就是今天这个修不好的 `_ranked`。

## 2. 为什么这不是"融合两次"

ADR-016 与 `ports/vector_index.py` 都写着不在适配器里融合，理由是**"第二次融合会造出
两个检索器都没产生过的排序"**。那条理由是对的，而且现在依然成立——它禁止的是对**已经
融合过的结果**再排一次，或者把两份各自截断过的列表再拼一次。

本决定不做那件事。融合次数仍然是**一次**：两次查询各自返回的是**原始的单臂结果**，
没有任何一方融合过；RRF 在适配器里对这两份原始名次算一次，然后结束。变的是这一次发生在
哪里，不是发生了几次。

移动它买到的东西只有一样，但没有别的办法买到：**臂内名次由我们决定**。两臂各自先过
`_ranked`（`(-score, chunk_id)`），于是并列点的名次来自 chunk_id 而不是引擎内部布局，
而 chunk_id 是从 chunk 派生的，重建索引后不变。

`k` 取 2 是为了和 Qdrant 服务端原本的取值一致，这样这次改动只改"名次怎么定"，不顺手
改掉评测基线的量纲。

## 3. 代价，写在明处

**多一次网络往返。** 两次查询用 `asyncio.gather` 并发发出，墙钟接近一次，但连接数与
请求数确实翻倍。这是为可复现付的价，不假装它不存在。

**评测数字需要重跑。** 38 题 gold set 上 MRR 0.960 / recall@1 0.947 是在服务端融合下测
的。改动后必须重测——但要说清楚：那组数字本来就是一个不可复现的检索器的一次抽样，
`_ranked` 的 docstring 自己记着"重复一次查询，9/38 的题给出不同 chunk 次序、3/38 给出
不同 top-3 文档"。用一个稳定的数字替换一个抽样，不是把基线弄脏，是第一次让它有基线。

**ADR-017 第 3 步的堵点因此可以重新推进**，但本决定**不**顺手把
`rag.llama_index.enabled` 改成 `true`：等价评测还没重跑，没有证据的开关不能翻。

## 4. 明确不做

- 不改 `VectorIndexPort` 的方法签名与 `ScoredChunk` 的字段；
- 不改两臂各自的 `dense_limit` / `sparse_limit` 语义（各自提出完整候选集，由 RRF 收敛）；
- 不引入可配置的 `k` 或可选的融合策略——两个融合实现就是两条要各自被评测的检索路径；
- 不动 dense 路径。它今天的定序是对的，实测可复现，这次改动一个字不碰它。
