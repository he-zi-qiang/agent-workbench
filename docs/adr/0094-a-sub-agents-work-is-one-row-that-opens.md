# ADR-094：一个子代理干的活是一行，展开才是九行

- 决策点：委派之后，子运行的事件和父运行的事件躺在同一个阶段里（子 scope 逐字段
  沿用父的 `graph_node_id`，只换 `run_id`），而时间线是平的。现状是给每一行标题加
  「子代理 analyst：」前缀——`web/src/features/work/delegations.ts` 自己写明这是替身，
  「折叠成段更好，代价是要改每个阶段都经过的那个共用步骤组件」。要不要改那个共用
  组件；如果改，`StepStream` 与调用方之间那条「阶段由调用方推导、组件只负责画」的
  分工怎么保住；以及一页缺失的 `AgentDelegated` 让页面说不出子运行叫什么时怎么办
- 状态：**接受**。新增 `components/runSections.ts`（把一个阶段的事件按 `run_id` 切段，
  再把**别人的**运行各自并成一块，父运行的段一条不动——见 §3）与 `StepStream` 的可选
  prop `runLabel`；不给这个 prop 时渲染结果与从前逐字节相同（Chat 就不给）。**删除** `titleWithDelegation` 与它的前缀。
  **明确不做**：不合并父运行自己的段（§3）、不在组件里推断运行的名字（§2）、
  不给这一层加任何新的取数（§5）

## 1. 缺口：九行各自重复同一件事

一次委派在时间线上是这样的：父运行准备上下文 → 发出委派 → 子运行开始、作答、
调工具、写报告 → 父运行接着往下走。这些事件**全部落在同一个阶段里**，因为
`adapters/delegation.py` 造子 sink 时逐字段沿用父 scope，只换 `run_id`。

此前的记号是给每一行标题加前缀：

```
子代理 analyst：运行已开始
子代理 analyst：模型作答
子代理 analyst：工具调用失败
…
```

读者真正要问的是「那个子代理干完了没有、烧了多少」。那是**一行**的问题，而前缀把
它摊成了九行，每一行都在重复同一个答案。

## 2. 决定：切段是机械的，命名不是

`StepStream.tsx` 的文件头写着一条分工：

> What is *not* shared is where the stages come from. … each caller derives its
> own stages and this renders them.

本 ADR 沿这条线切：

- **切段归组件。** `event.run_id` 变了就是换人了，这是事件自带的事实，不需要任何
  产品知识。所以 `splitByRun` 在 `components/` 下，`StepStream` 自己调。
- **命名归调用方。** 「这个 `run_id` 是一次委派，被派出去的叫 analyst」要读
  `AgentDelegated`，而 Chat 的一轮里连这个事件都不会有。所以 `runLabel` 是 prop，
  由 `WorkPage` 用 `readDelegations` 与 `runTree` 拼出来。

`runLabel` 是**可选的**，不给就完全不分段。Chat 不给，于是 Chat 的渲染结果与从前
逐字节相同——这不是兼容性妥协，是「Chat 的一轮里只有一个运行，分段对它是无意义的
一层」这句话的实现方式。

## 3. 一个子运行一块；父运行的事件一条都不挪

**这一节是被真数据改过的，原来的结论错了，所以两个版本都写在这里。**

第一版是纯连续分段：`run_id` 一变就切一段，谁也不合并。论证是「归堆会把父运行在
委派之后做的事挪到子运行前面去，而这条流存在的全部理由就是顺序」。这个论证的前半
句是对的，后半句把它用错了地方。

拿 `task_75cd1e0c` 实测——那是 C-08 关闭时跑出来的那次，四个 `analyst`，
`max_parallel_child_invocations = 2`。它在 `work` 这个节点上的事件按运行连出来是：

```
P×15 → c1×1 → c2×1 → c1×1 → c2×1 → c1×2 → c3×1 → P×1 → c3×1 → P×1 → c2×2 → P×2 → c3×2 → P×16 → c4×4 → P×11
```

三种合并策略在这条真数据上的结果：

| 策略 | 子代理块 | 每块的事件数 |
| --- | --- | --- |
| 连续分段（第一版） | **10** | 1, 1, 1, 1, 2, 1, 1, 2, 2, 4 |
| 兄弟可跨、父运行是屏障 | 7 | 4, 2, 1, 1, 2, 2, 4 |
| 同一阶段内合并别人的运行 | **4** | 4, 4, 4, 4 |

四个子代理各写了四条事件。连续分段把它们摊成十个一两条的小块，浏览器里数出来是
11 个（另有一个页面认不出名字的运行）。

**为什么第一版的论证用错了地方：并发的两个 agent 之间没有顺序可读。** c1 的第二步排
在 c2 的第一步前面，是调度器的产物，不是任何人做过的决定。把它画成十个交替的块，是
在暗示一场它们之间并不存在的对话——那比归堆更失真。

所以规则收窄成：**只合并不属于这个阶段自己的运行，父运行的段一条都不动。** 父运行的
事件之间有真正的先后（它委派、它等、它拿到结果、它接着做），那一半的顺序原样保留，
第一版论证要保护的正是它。

代价照直说：一个子代理的块代表的是**一段时间**而不是一个瞬间，块里最后一条事件可能
晚于排在这个块下面的某些父运行事件。实测中被跨过去的父运行事件是什么，也查了——是
`delegate_agent` 这次工具调用自己的生命周期（`ToolProposed` → `PermissionResolved` →
`ToolStarted` → `AgentCompleted` → `ToolCompleted`），也就是**关于这些子代理的记账**。

## 4. 叫不出名字的运行也要装进框里

这是取代前缀之后**唯一不能丢**的那半，而它很容易被丢掉。

`readDelegations` 只从 `AgentDelegated` 建立「子运行 → 名字」的映射。一页没送到的
`AgentDelegated` 会让页面说不出某个 `run_id` 是谁的——而那时候把它的事件画成父运行
干的，是这里**唯一错的答案**。旧前缀在缺页时正是静默退化成那个样子。

所以 `runLabel` 返回 `null` 的段照样装进框里，标题用 `运行 xxxxxxxx` 兜底，并且
**不挂「子代理」徽标**：那块只知道「这些事件来自另一个运行」，挂上徽标就是替它做了
一个它答不出的断言。徽标因此是 `StreamRunLabel` 的一个字段、由调用方给，而不是组件
看见「这一段是别人的」就画上去。

**而在真数据上还有第三种。** 同一条实测（`task_75cd1e0c`）里，`review` 这个图节点
**跑了两次**——20 条事件一次、4 条一次，两个都是根运行，谁也没被委派。第一版把第二次
装进框里标成 `运行 run_…bab4`：真话，但读者拿它没办法。

页面其实答得出更好的：`runTree` 里同一个 `nodeId` 下的根运行按 `firstSequence` 排一下
就是第几次。所以现在它标 `第 2 次运行`，**不挂徽标**——它不是任何人的子代理，装框只
说「这一段来自另一次运行」这一件事。

这一条顺带把一件以前完全看不见的事说了出来：那个阶段的 24 行此前是一列平的，没有任何
东西讲过它其实是两回。只数根运行是必须的——被委派出去的那些 `nodeId` 沿用父运行的，
一起数会让「第 2 次运行」指到一个子代理身上。

## 5. 每一段各自分组，而不是先分组再切段

`stepGroups` 的组 key 是 `tool:${tool_call_id}`，**不含 `run_id`**（同仓库的
`workTimeline.toolCallKey` 刻意加了 `run_id` 命名空间，这里没有）。所以先分组再按组
切段的话，父子两个运行产出同号 `tool_call_id` 时会被折成一个组，然后整个组只能落在
某一段里——**一次调用凭空归给了另一个 agent**。

逐段分组时这件事不可能发生。阶段那一行的摘要也从同一批组算，否则一个阶段可以显示
「3 步」而展开之后是 4 行。两条都有测试。

## 6. 先补网，再动手

这个共用组件被 Work 与 Chat 用着，而在这一批之前它**一条渲染测试都没有**：
`stepGroups`、`activityPresentation`、`runTree` 各有自己的纯函数测试，组件本身一个
断言都没有。「改共用组件」在这个仓库里一直被估得很贵，而贵的原因不是它难，是**改完
没有任何东西会告诉你它还对不对**。

所以 `StepStream.test.tsx` 先钉的是它**现在的行为**（阶段怎么排、什么时候展开、组
折不折、空阶段、`meta` 那一折、认不出的事件带记号），11 条；分段那一层的 12 条排在
后面。上一批把这件事记成「不做，因为没有那张网」——网是可以自己织的，那不是不做的
理由。

## 7. 它和 `RunPanel` 不重复

两块面板，两个问题：

| | 问题 | 排法 |
| --- | --- | --- |
| `RunPanel` | 谁在干活，各自干到哪了 | 一行一个运行，按谁派了谁嵌套 |
| 时间线的运行块 | 按发生顺序，这一段是谁干的 | 按时间，穿插在父运行的步骤中间 |

`RunPanel` 的文件头本来就写着它存在的理由是「那条流交错了两个 agent 的调用，怎么排
都读不出子代理干得怎么样」。本 ADR 没有推翻这句话——它做的是另一件事：让那条流在**按
时间读**的时候也说得出这一段是谁干的。一个是花名册，一个是流水。

## 8. 被拒绝的方案

**在 `StepGroup` 上加一个 `runId` 字段，然后按它切。** 改动看起来更小，但
`StepGroup` 是 Code 页也在用的公共类型（`turnBlocks.ts`、`CodeTurn.tsx`），而且它撞上
§5 那条：分组发生在切段之前，撞号的问题原样保留。

**让 `StepStream` 自己从 `run_id` 推断名字。** 那要它认识 `AgentDelegated`，也就是让
一个「只负责画」的组件开始读产品语义，直接违反它文件头那条分工；Chat 还得为一个它
永远不会有的事件类型付这份代码。

**保留前缀，只在块的表头上加名字。** 两个记号说同一件事，而九行前缀里没有一行是新
信息。

**把子运行的事件挪到阶段末尾统一放一块。** 读起来最整齐，代价是把父运行的顺序也一起
重写了——§3 保住的正是那一半。

**纯连续分段，一段都不合并。** 这是第一版，被真数据推翻，数字见 §3。
