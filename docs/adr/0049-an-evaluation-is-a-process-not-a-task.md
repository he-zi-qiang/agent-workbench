# ADR-049：评测是一个进程，不是一个 Task；它的证据是报告文件，不是一行状态

- 决策点：控制台要能发起评测——那个"运行"该建模成什么；它的状态存在哪；重启之后
  它变成什么
- 状态：**接受**
- 日期：2026-08-16
- 影响：新增 `evaluation.runs_enabled` / `reports_root` / `run_timeout_seconds` /
  `max_concurrent_runs`（单值 `Literal[1]`）；`ports/evaluation_runs.py`、
  `adapters/evaluation/subprocess_launcher.py`、`application/evaluation.py`、
  `apps/api/routes/evaluation.py`；评测页从构建时静态 import 改为读 API
- 依赖：ADR-039（一个指标名是一种承诺）、`docs/known-gaps.md` F-01（Code 拒绝租约与收割器）

## 1. 不是 Task

`TaskState` 是一组图通道。Task 子系统带着预算、checkpoint、泳道、租约和审批，
因为**一张图**必须能在 worker 死掉之后接着跑。

评测是一个读固定语料、写 JSON 的脚本。把它包成单节点图，会继承一份我们随后必须
撒谎的恢复契约——从中间恢复对 `run_rag_eval.py` 没有意义，它不是幂等的：一次
"恢复"就是重新索引一遍语料。

## 2. 也不是一张持久 run 表

一张能对死进程说真话的 run 表需要租约和收割器。Code 已经在 F-01 里拒绝过同一套
机器，理由相同：那是为了让一行状态不撒谎而引入的第二套分布式协调。

而且它买不到东西。`scripts/run_rag_eval.py` **每跑完一个 arm 就立刻把报告写盘**
（第 335–340 行的循环），所以一次跑到一半被杀的运行留下的是**已完成 arm 的真实
完整证据**。在这个仓库里，报告文件就是证据的单位——一张 run 表会是第二个、更弱的
单位，而两个单位迟早会互相矛盾。

所以运行活在发起它的那个进程里，随那个进程死。API 明说这一点：
`GET /runs/current` 返回 `null` 时，含义是"这个进程没有起过"，而**不是**"从来
没人跑过"——磁盘上的报告仍然在。

## 3. 报告整份透传，一个键都不改

`ReportView.payload` 是 runner 自己那个 JSON 对象，原样。

第一版只挑了 `scores` 出来，那是错的，而且是被"拿它去写前端"这件事发现的：页面
需要 `gold_digest` 和 `question_count` 才能说清一个数字回答的是哪套题，而一个只
挑 `scores` 的层已经替所有未来的读者和所有未来的 suite 决定了"一次测量里哪些部分
重要"。这和 ADR-039 禁止改指标名是同一条理由——改名是撒谎，挑字段是替人做主。

三个 suite 的指标集本来就不同。归一化成一个形状会让"这两个数可比"这句话由这一层
凭空说出来，而它没有测过任何东西。

## 4. `max_concurrent_runs` 是冻结的 1

这是一次测量，不是一个偏好：一整轮 RAG 消融会加载 BGE-M3，在开发这个仓库的机器上
要 30–70 分钟，而第二个并发 arm 是 OOM kill 而不是"跑得慢一点"。

要把它调大，需要一份说清"为哪台机器调大"的 ADR。写成单值 `Literal` 而不是 `int`，
是因为这个仓库把冻结的 `Literal` 当架构门：一个能在 TOML 里改的数字，会让下一个人
以为 2 只是慢一点。

## 5. suite 名永远到不了命令行

请求 body 里是一个 `Literal` 的 suite 名；服务端拿它去查一张**固定的 argv 表**。
两层都有测试：一条断言 `{"suite": "rag; rm -rf /"}` 被 schema 挡成 422，另一条
断言 `COMMANDS["rag"]` 就是那个固定元组——前者证明今天穿不过来，后者证明就算
schema 哪天被放宽了，也没有字符串格式化可以穿。

`sys.executable` 跑的是 API 自己的解释器。缺 `embedding` extra 的部署因此在几秒内
非零退出，它自己 stderr 的尾巴就是控制台显示的东西——这比一个存着 shell 命令、
需要被引号处理、切分和信任的配置字段诚实。

## 6. `runs_enabled` 默认 false

一个会答 500 的按钮比没有按钮更糟。跑一次需要 embedding 运行时和一个可达的
Qdrant，而"能提供 HTTP 服务"不蕴含这两样；Docker 镜像里脚本可能根本不在。

关掉时页面给的是**那条确切的命令**，不是一个变灰的按钮：变灰说的是"以后可以"，
而真相是"去别处"。

**读报告不在这道门后面。** 一个跑不了评测的部署仍然能显示已经提交的数字，而把那些
也藏起来等于藏起它唯一有的证据。

## 7. 一个搬迁，不是一次删除

评测页原来在构建时静态 import 四个 JSON，而那个安排有个真实的好处：删掉一份报告
会让 `tsc` 失败，而不是显示一个陈旧的数字。

那道检查没有被丢掉，它搬了两个地方：
`tests/api/test_evaluation_api.py::test_the_committed_reports_still_parse` 断言那
四份文件仍然能解析；前端测试仍然 import 同样四个 JSON 当 fixture，喂给假 API。
删掉任何一份，两边都会红。

## 8. 什么会让这条决定重来

**评测跑在一台不同时服务控制台的机器上那天。** §2 的推理依赖"运行和 API 在同一个
进程里"——一旦不是，就需要一个队列、一张 run 表和一个收割器，而那时它们不再是多余的
机器，因为没有别的东西知道那台机器上发生了什么。

**报告不再逐 arm 落盘那天。** §2 的整个论证建立在"跑到一半留下的也是完整证据"上。
一个只在最后一次性写盘的 runner 会让这句话为假，那时一行状态就变成了唯一的进度信号。
