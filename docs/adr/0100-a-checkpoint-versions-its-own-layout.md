# ADR-100：检查点给自己的布局编号，不借用域的那个

- 决策点：改动 `TaskState` 里任何一个模型的任何一个字段，都会让部署时每一个在飞的
  Task 无法恢复，而这条路上**没有任何迁移机制**；是给检查点补一条升级路径，
  还是接受「域模型冻结」并写明「改之前必须排空在飞的 Task」
- 状态：**接受**，补升级路径，**并让检查点用自己的布局版本号**，不复用
  `DOMAIN_SCHEMA_VERSION`
- 日期：2026-08-31
- 影响：新增 `adapters/langgraph/checkpoint_migrations.py`；`GraphState` 新增一个
  **非域字段**的通道 `checkpoint_schema_version`；`_to_state` 在校验前升级一次。
  第一条升级步就是它的第一个真实用户——删掉 `TaskStep.depends_on`（已知缺口 B-10
  的最后一处）。**事件那条路一个字都没动**（见 §3.1）
- 依赖：[ADR-035](./0035-an-answer-is-not-a-preview.md) 与已知缺口
  [B-05](../known-gaps.md)（事件 upcaster）、
  [ADR-014](./0014-own-postgres-checkpointer.md)（自建 checkpointer）

---

## 1. 背景：两条恢复路径，只有一条能迁移

一个 Task 的位置存在两个地方：

| | 事件回放 | 检查点恢复 |
|---|---|---|
| 存的是什么 | `run_events` 里的事件信封 | LangGraph 通道，由 serde 存取 |
| 读回来会不会被校验成域对象 | 会 | 会——`_to_state` 做 `TaskState.model_validate` |
| 有没有升级机制 | **有**：`EventUpcasterRegistry` | **没有** |

`TaskState` 是 `DomainModel`，因而 `extra="forbid"`。所以**改动它内部任何模型的任何
字段——加、删、改名——都会让改动之前写下的每一个检查点无法载入**，而持有它的 Task
无法恢复。实测，不是推断：喂 `_to_state` 一份多带一个键的 plan dict，
得到 `extra_forbidden`。

**这条缺口一直没被发现，是因为它长得像另一条已经登记过的。** 本仓库有 upcaster，
而且[已知缺口 B-05](../known-gaps.md) 专门记着它的注册表是空的——于是「检查点改字段
会坏」很容易被读成「B-05 的一个实例」。不是：那套注册表由 `PostgresEventLog` 应用在
**存储的事件信封**上、发生在回放的时候，**检查点从不经过它**
（`adapters/langgraph/` 里 `upcast` / `migrat` 零命中）。

## 2. 为什么不复用 `DOMAIN_SCHEMA_VERSION`

第一反应是：`TaskState` 已经有 `schema_version` 了，抬它就是了。

**抬它会把事情弄得更糟，而这是本 ADR 最要紧的一段。**

`DOMAIN_SCHEMA_VERSION` 是**全局**的——每一个 `VersionedModel` 共用它，事件信封也是。
而 `VersionedModel.reject_unsupported_schema_version` **失败关闭**：

```
VERSION BUMP ALSO REFUSED: ['schema_version']
```

于是抬版之后：

- 每一条**已存的事件**都声称着一个读者拒绝的版本；
- 能救它们的事件注册表**是空的**（B-05）；
- `raise_to_current` 遇到没有登记的步骤会停在洞前、保持拒绝——
  **也就是把整段事件历史隔离掉**。

**一个为了让迁移可能而存在的字段，在这条路上让迁移变成不可能。**
一根轴扛不了两段互相独立的历史：plan 的形状变了，与任何一种事件的形状变了，
是两件事。

## 3. 决定

### 3.1 检查点有自己的布局版本

`CHECKPOINT_SCHEMA_VERSION`，起始值 **2**。**1 表示「写于这个字段存在之前」**
——今天在库里的每一个检查点都没有这个键，而**缺席就是版本 1**，不是错误。
任何地方都不存在一个写着 1 的戳。

它是一个 `GraphState` 通道，**不是 `TaskState` 的字段**：域不知道自己被检查点存着，
把它做成模型字段等于把框架细节塞进契约。`_to_state` 在校验前把它剥掉，
和它剥掉 LangGraph 自己的 `__` 通道是同一个动作。

`tests/workflows/test_langgraph_workflow.py` 的通道守卫因此拆成两半：
每个 `TaskState` 字段都必须有通道（原来的意思），
以及**不是域字段的通道必须逐个列名**——否则这里就成了夹带的口子。

### 3.2 键只按 `from_version`，不按类型

事件的链要 `(event_type, from_version)`，因为信封有很多种。检查点只有一种形状
（图状态），类型那一半在每个键里都会是同一个常量。所以是一张**独立的小注册表**，
而不是把事件那张改宽——改宽会得到一张一半键恒定的表。

链**自己**管版本推进，单步只管改形状：一个自己负责盖戳的 upcaster 可能忘记盖，
那样循环会把同一步永远做下去。这一条是照抄事件那张表的，它当时就是对的。

### 3.3 两种拒绝，都写明理由

- **版本高于当前**：由更新的部署写下，这个进程不知道它删掉了什么，拒绝；
- **链上有洞**：点名拒绝。缺一步是有人忘了写迁移，蒙着过去等于把一份
  声称着某个形状的载荷交给校验。

### 3.4 第一条升级步就是它的第一个真实用户

**一个注册表为空的迁移机制，正是它要防的那种东西**——B-05 就是这么一条已知缺口。
所以本 ADR 不只落地机制，还带着第一条真实迁移：`TaskStep.depends_on` 的删除。

那个字段被四道校验守着、`TaskPlan` 还有第五条规则、planner 契约明确要求模型产出它，
**而没有任何东西执行它**：计划被渲染成扁平编号，图的形状提交时就冻结、不按步骤分支。
删它一直被这条缺口挡着（[已知缺口 B-10](../known-gaps.md) 的第七处）。

## 4. 后果

### 4.1 拿到了真实数据上的证据，而这正是 B-05 缺的那一半

本机开发库里有 218 个 `plan` 通道 blob，其中 **85 个非空、共 305 个计划步，
每一个都带着 `depends_on`**。逐个跑过：

| | |
|---|---:|
| 真实非空计划 | 85 |
| 真实计划步 | 305 |
| **不经迁移**能载入的 | **0** |
| 经迁移能载入的 | **85** |

**0 → 85。** 也就是说：不做这条迁移而直接删字段，这台机器上每一个带计划的检查点
都会变成一个恢复不了的 Task。

**这不能替 B-05 结账。** 拿到证据的是**检查点**这条路；事件那条的注册表仍然是空的、
仍然没在真实数据上走过。两条路，两份证据。

### 4.2 域模型不再是冻结的，但代价换了个位置

此前「不要动 `TaskState` 里的字段」是一条没人写下来的规矩。现在动它是可以的，
**代价变成：每一次动都要写一条升级步，并且这条链永远不能有洞。**
`test_the_shipped_chain_reaches_the_current_layout_from_every_version` 守着这一点——
链上一个洞就是一批恢复不了的 Task。

### 4.3 明确没做

- **没有给事件那条路补东西。** B-05 保持开着，措辞不变。
- **没有回头改已存的检查点。** 迁移发生在**读的时候**，库里的字节一个都没动——
  一次批量重写会在没有事务边界的地方碰 1046 行，而读时迁移是幂等的。
- **没有给旧布局设保质期。** 层 1 的步骤会一直留着；哪一天可以删，取决于
  「最老的在飞检查点有多老」，而这个问题今天没有数据能回答。

## 5. 重审条件

若将来某一次布局变更**不是**能靠丢字段完成的（比如一个字段要改类型、或者要从别处
推导出来），那时要回答一个本 ADR 没有回答的问题：升级步能不能失败，以及失败的检查点
是隔离还是拒绝。事件那条路已经答过（`read_isolating`，隔离且可见），
**而检查点没有"隔离一条"这个选项**——一个 Task 的位置是整体的。
到那时这条链可能需要一个「拒绝并说明」的终态，而不是只有成功一种。
