# ADR-031：通用任务走第二张图，而不是把研究流水线改宽

- 决策点：一个不是"写调研报告"的任务该走什么形状；模型能不能决定自己的步骤顺序
- 状态：**接受**
- 日期：2026-08-09
- 影响：新增 `graph_version = "v2_general"` 与它的四个节点；`research_graph.py` 与
  `CANONICAL_V1_NODE_IDS` **一个字不改**；提交 Task 时可选图形态
- 依赖：ADR-028、ADR-029、ADR-030（v2 的工作节点没有工作区、沙箱和成本预算就没有意义）

## 1. 背景

v1 的图是一条为**调研报告**设计的流水线：

```
understand → plan → route → research_internal/external → synthesize → critic
→ quality_gate → approval → export
```

它对那件事是合适的，而且它的形状本身就是这个项目要展示的东西：两个 researcher 并行且
互不可见、critic 只看草稿不看证据、审批只管导出。这些约束是资产，不该被稀释。

问题是"把三个 CSV 合并成一份对账表"这类任务走进这张图会发生什么：它会被迫先做两路检索
（无内容可检）、再"综合证据"（没有证据）、再被一个为文章写作准备的 critic 评审。**每个
节点都会执行，每个节点都不解决问题**，而使用者看到的是一个跑了十步、花了钱、产出一份
不知所云的报告的任务。

把 v1 改宽是最坏的选项：它会把上面那些**具体的**约束，改成"看情况"。

## 2. 决策

### 2.1 加一张图，不动第一张

`workflow.graph_version` 已经是 `str` 而不是冻结的 `Literal`（`settings.py:412`），配置层
早就允许不止一张图。今天只是没有第二张。

新增 `v2_general`，四个节点：

```
understand → work → review → export
```

- `understand` 与 v1 同名同职，不共用代码（v1 的实现绑着它自己的 state 形状）；
- **`work` 是一个带完整工具集的 Agent run**：工作区、沙箱、只读取用、渲染器。模型在这
  个节点内部自己决定顺序——读什么、跑什么、重试几次、什么时候算完；
- `review` 检查产物是否满足目标，不满足则回到 `work`，与 v1 的 `quality_gate → synthesize`
  同一个形状，`MAX_REVISIONS` 同一道闸；
- `export` 与 v1 同一条路径、同一个 HITL 审批、同一个副作用账本。

`CANONICAL_V1_NODE_IDS` 一个字不改。v2 有它自己的节点常量。

### 2.2 模型决定的是节点内的步骤，不是图

这是本 ADR 与"让 Agent 自由编排"的分界，也是它不必重审 ADR-009 的原因。

图仍然是唯一的跨 Agent 编排者，仍然在节点边界 checkpoint，仍然是重放的单位。变化只有
一处：**v2 有一个节点，它内部的步骤数不是 1**。而这在今天已经成立——
`writer/synthesize` 本来就是 `ClaudeLikeAgentRuntime` 的工具循环。v2 只是让这个循环拿到
足够的工具和足够的预算（ADR-030）去把一件事做完。

所以"像 Claude Code 那样自己决定下一步"这件事，在 v2 里是成立的——**范围是一个节点**，
而这个节点的失败、重放和审批语义与其他节点完全一致。

### 2.3 走哪张图由提交决定，不由模型猜

`POST /v1/tasks` 增加一个可选字段选择图形态，默认仍是 v1。

**不做自动路由。** 让模型看一眼目标就决定走哪条流水线，是把一个使用者清楚知道答案的
问题交给一个会猜错的东西，而猜错的代价是整条流水线跑错。这与 ADR-021 那条推理一致：
"要不要联网"由检索结果的可测量事实决定，不由模型自陈。

图形态与授权信封一样，**提交时冻结并存进 Task**：一个已经在跑的 Task 不会因为部署改了
默认值而换一张图。

### 2.4 v2 不放宽任何边界

同一个 Tool Gateway、同一个授权信封、同一条 artifact 通道、同一个导出审批、同一套预算。
v2 与 v1 的差别**只有节点拓扑**。

特别地：v2 的 `work` 节点**不会**因此拿到写外部世界的能力。ADR-027 那条线对两张图一样
成立。

## 3. 后果

- "做一件事"这类任务第一次有了合适的形状，不必假装自己是一篇调研报告；
- v1 的那些具体约束被完整保住，因为它没有被改；
- **代价是两张图要一起维护**：恢复、审批、事件、预算这些横切的东西每加一处都要在两张图
  上都成立，而一张图漏掉是很容易发生的。缓解办法是共享节点实现而不是复制，并且让
  `declared_nodes()` 那类结构测试对两张图都跑；
- 提交时多一个决定要做。默认值保证既有调用方不受影响；
- **不解决**：图之外的自由编排、动态生成节点、跨图共享状态。

## 4. 备选方案

**把 v1 改宽，让检索和 critic 在没内容时跳过。** 最省事，代价是把"两个 researcher 并行
且互不可见""critic 只看草稿"这些具体的、可讲述的约束，变成一串"看情况"。这张图的形状
本身就是作品要展示的东西，稀释它等于把最值钱的部分改掉。

**只加一个节点，不加图。** 在 v1 里插一个 `work` 节点仍然要经过两路检索和文章 critic，
问题没解决。

**让模型自动选图。** 见 §2.3。

**干脆不要图，只留一个 Agent 循环。** 那是另一条路线，代价在别处论证过：整个持久化、
恢复、审批和可审计性都建立在"图节点是重放单位"之上。
