# ADR-103：附加的零件可以从控制台上拨动，拨的是下一次启动

- 决策点：ADR-102 的能力清单是只读的，它的 §4.4 明确写着「不给这份报告加写口」。
  使用者看着一排灰色的「缺失」问了一个合理的问题：附加项既然像零件，为什么看得见却
  选不了——要不要让控制台能拨动它们，以及拨动意味着什么
- 状态：**接受**。四个**开关型**零件可以拨，拨的是**下一次启动**；安装型零件只标
  「需要安装」，没有开关。**部分推翻 ADR-102 §4.4**，推翻的边界写在 §4
- 日期：2026-09-01
- 影响：新增 `application/switches.py`（开关表、`switches.json` 的解析与原子写）与
  `bootstrap/switches.py`（文件在哪、容器启动脚本的判定）；`load_settings` 新增第五个
  显式入参 `switches_file`，以及一条「搁置」规则；`Settings` 新增三个类属性
  （`stored_switches` / `applied_switches` / `held_switches`）；`ApiRuntimeConfig`
  新增 `switches` 与 `switches_file`；`GET /v1/system/capabilities` 每行多出
  `provision` 与 `switch`；新增 `PUT` / `DELETE /v1/system/switches/{id}`；控制台每个
  开关型零件一行三位开关；`docker/provider_key_present.py` 改名 `decide_web_search.py`
  并为存下的选择让路；Compose 的两个 Worker 挂上 key 卷；`scripts\stack.cmd restart`
- 依赖：[ADR-101](./0101-the-console-may-hand-over-a-key-it-can-never-read-back.md)
  （同一形状：写到 checkout 之外、只对下次启动生效、「已存下」与「正在用」两个布尔）、

## 1. 背景：看得见，选不了

ADR-102 让一台部署说得出自己没装配起什么。Windows 上双击 `scripts\stack.cmd` 起来的
栈，「运行状态」页从此列出十二行：五行核心，七行附加，每一处缺失带原因、带补法。

补法是一句话，而那句话要人去做的事分两种，页面上却长得一样：

| 补法说的是 | 例子 | 一个人要动什么 |
|---|---|---|
| 改一个布尔 | 「让 API 带 `AW_RESEARCH__ENABLED=true` 启动」 | 找到启动脚本、找到那个变量名、改、重启 |
| 装一样东西 | 「需要装了 embedding extra 的镜像」「启动 Word/web MCP 服务」 | 换镜像、起服务、改拓扑 |

第一种里没有任何一步需要离开控制台才能知道——变量名就写在页面上，值只有两个。
让人为了一个布尔去翻 `compose.yaml`，是把「看得见」的价值折掉一半：一份清单告诉你
缺什么、怎么补，然后停在你面前。

使用者的原话是「附加的就像零件，可以看见和选择」。这份 ADR 接受这个比喻，并且把它
说精确：**零件分两种，只有一种是选一下就有的**。

## 2. 零件分两种，只有一种有开关

每一行多一个字段 `provision`，说这个零件是怎么来的：

| `provision` | 含义 | 行 |
|---|---|---|
| `switch` | 一个布尔，其余的东西镜像里都有；拨下去，下次启动就装配 | 对话联网搜索、任务联网搜索（**同一个开关**）、Code 会话、子代理委派、任务分流 |
| `install` | 要一台服务、一个 socket 或另一个镜像；这一页上没有任何东西能补上 | 知识库问答、知识库检索、MCP 工具、沙箱 |
| `key` | 只差 Provider Key，它有自己的那一格（ADR-101） | 直接对话 |
| `none` | 没什么可补 | 提交任务、任务 Worker |

四个开关，四个配置路径，一个不多：`research.enabled`、`triage.enabled`、`code.enabled`、
`multi_agent.delegation_enabled`。选它们的判据只有一条——**在设置模型里是一个普通的
`bool`，且它为真所需要的一切已经在进程里**。`sandbox.enabled` 也是个 `bool`，但它为真
意味着一台能开容器的 MCP 服务在跑，Compose 栈里没有；给它一个开关，是承诺一件这一侧
兑现不了的事。所以它是 `install`，页面上标「需要安装」，补法照旧写清楚。

开关的 id 就是配置路径。`switches.json` 里写的是 `{"research.enabled": true}`，去掉前缀
和分隔符之后和 `AW_RESEARCH__ENABLED` 是同一个拼法——一个人找到这个文件，立刻知道它
动的是哪个旋钮，`grep` 设置模型就能找到。**两个方向都拒绝不认识的键**：解析器由存储
和加载器共用，新版控制台写下一个旧版进程不认识的开关，旧版进程会在启动时把文件名和
那个键说出来，而不是默默丢掉、让页面展示一个没人兑现的选择。

## 3. 拨的是下一次启动，不是这个进程

### 3.1 两个布尔，不是一个

进程在组装期读一次配置，之后什么都不会变——这是 ADR-101 §3.2 为 key 说过的话，对四个
开关一字不改。所以每个开关有 `stored`（文件为下次启动记的值，`null` 表示什么也没记）
和 `active`（这个进程正在用的值）两个字段，页面上写成「这次启动：关 · 下次启动：开」，
外加 `restart_required` 与那句和 key 一模一样的提示：重启 `agent-api` 与
`agent-task-worker` 后才生效。

`null` 是第三个位置，页面上叫「不指定」，而且它是**真实的状态**：下次启动照环境变量和
配置文件走。在 Docker 栈上，那意味着 ADR-102 §3 那个「探到 key 就打开联网搜索」的启动
脚本继续决定。把它画成「关」，是让页面替启动脚本作它没作的决定。

### 3.2 存下的开关排在哪

```text
进程环境变量
> mounted secret files
> .env
> 控制台存下的 provider key（ADR-101）
> 控制台存下的开关（本 ADR）          ← 新
> AW_CONFIG_FILE 指定的 TOML overlay
> config.default.toml
```

在 TOML 之上，因为出厂文件对四个开关写的全是 `false`——一个输给出厂文件的开关是
一个谁也拨不动的开关。在环境之下，因为操作者导出的值是这台部署自己的决定；页面把
「文件说开、进程却关着、而且不是被搁置」这种情况报成 `overridden`，写明「启动环境里
显式给了这个值，压过了这里的选择」，而不是装作能改。`scripts/dev.sh demo-api` 无条件
导出 `AW_RESEARCH__ENABLED=true`，就会落进这一格；那个脚本不改，页面说实话就够了。

### 3.3 搁置，而不是拒绝启动

`research.enabled` 在没有 key 时是启动错误（settings 里那条「配置描述了一个不存在的
系统」）。ADR-102 §3 为此把容器启动脚本挡在这个开关外面：写死 `true` 会让全新的栈起不
来，而存 key 的页面就在那个拒绝启动的进程里。

给控制台一个能写 `research.enabled=true` 的开关，等于把同一个陷阱搬回来，只是这次
挖坑的是使用者自己。所以加载器多了一条规则：**一个存下的「开」，如果验证器会因为没有
key 拒绝它，就搁置它**——不应用、照旧存着、记下原因、让那一行说出来（「这次启动没有
可用的 Provider Key，所以这个开关被搁置：它仍然存着，存了 key 再重启就会生效」）。

判定用的是验证器自己的规则，不是它的复述：加载器先**不带这个开关**构造一次设置，问那个
对象 `provider_key_is_configured()`——这一问走的是真实的优先级，`.env` 和 mounted secret
都算在内——再决定带不带它构造第二次。代价是被搁置那一次多一次 TOML 解析，只发生在
显式传了 `switches_file` 的入口（`agent-api`、`agent-task-worker`），测试套件和
`agent-config-check` 从不传。

只有 `research.enabled` 有这条规则，写在 `SwitchSpec.held_without_key` 上。另外两个
需要模型的开关（`triage`、`code`）没有 key 时不会拒绝启动，只是装配不出来；它们的行
在开关旁边提前说「这一项要有模型才装配得起来」，写入不被拒绝——**文件记的是一个愿望**，
搁置和阻塞都是「愿望还没被兑现」的两种说法。

### 3.4 启动脚本让路

`docker/run-api-local.sh` 那个探测保留，但**只在没人决定的时候**开口：环境变量未设或
为空，**且** `switches.json` 里没有 `research.enabled`。文件里记了值——开或关——探测
就退出，由加载器应用或搁置。探测改名为 `decide_web_search.py`，因为它回答的不再是
「有没有 key」，并且它把走了哪条路打到 stderr，`docker compose logs api` 看得见。

一个加载器读不了的 `switches.json` 让探测答「否」而不是给第二意见：加载器一秒钟之后
就会带着文件名拒绝启动，探测在那之上再打开联网搜索，只是在真正的错误前面多摆一个错误。

### 3.5 一个文件，一个卷，三个容器

开关文件放在 key 文件**旁边**（`switches.json`），位置由 `bootstrap/switches.py`
从 `AW_KEY_FILE` 推出。一个声明了「没有 key 文件」（`AW_KEY_FILE=""`）的部署，也就
声明了没有开关文件，存储会用同一句话拒绝写。Compose 里这意味着不用第二个卷：两个
Worker 挂上 API 已经在用的 `provider_key_data`，并拿到同一个 `AW_KEY_FILE`。`--demo`
Worker 两个文件都不用，但 Worker 是**注册**信封允许的那些工具的进程——这个标志哪天
摘掉，「联网搜索是开的」在两个容器里必须是同一句话。

`scripts\stack.cmd restart` 是同一件事在 Windows 上的最后一步：只重启 API 和两个
Worker——读配置一次的三个进程——PostgreSQL、Qdrant 和 collector 不动，几秒钟，而
`down` 再起会重新构建镜像。

## 4. 与 ADR-102 §4.4 的关系：推翻了什么，守住了什么

ADR-102 §4.4 说：「一个能从浏览器改能力的控制台，会让『这台部署是什么』不再有单一
答案。」这句话的前半段被推翻了，后半段没有。

**守住的**：「这台部署是什么」的答案仍然只有一个——这个进程在启动那一刻装配了什么，
由 `active` 与每一行的 `state` 回答，页面上没有任何东西能改变它。开关改的是**下一台**
部署是什么，而那从来就是可以改的：改 `compose.yaml`、改环境变量、改 TOML，都是在改
下一次启动。本 ADR 做的只是把其中最小的一种改法——一个布尔——从「翻文件」搬到了
「按一下」，并且逼着它把「已存下」和「正在用」分开说。这正是 ADR-101 对 key 已经做过
的事；那份 ADR 落地那天，§4.4 的绝对措辞其实已经站不住了。

**推翻的**：「页面上没有任何一个开关能改这里的任何一行」。现在有四个。ADR-102 的
其它三条「明确不做」（不加 Worker 上报通道、不报「工具真的能用」、不做认证）一字不动。

## 5. 明确不做的

1. **不热加载。** 与 ADR-101 §3.2 同一条理由：运行中重建模型客户端、重挂路由、改写
   任务信封的默认值，会让「一个进程提供什么」不再是启动时定死的——而那是这套设计刻意
   的选择。
2. **不做认证。** 前提与 ADR-101 完全相同：任何碰得到这个端口的东西都能拨这四个开关。
   它们不含凭据、不含地址，但它们确实改变下一台部署的形状。不缓解，写下来。
3. **不给安装型零件开关**，理由在 §2。也不给核心行开关：核心缺失是半个产品不在，
   不是一个选择。
4. **不产生事件。** 拨一个开关和存一把 key 一样，事件流里什么也没有。
   [D-07](../known-gaps.md) 的范围据此扩到开关；它的前提（没有真正的身份，一条「谁拨的」
   记录比没有更糟）一字不变。
5. **不改 `scripts/dev.sh`。** 它导出的 `AW_RESEARCH__ENABLED=true` 会压过存下的开关，
   页面会把这一格报成 `overridden` 并说出原因。让脚本读文件是可以做的，但那会让原生
   路径和容器路径各有一套「谁让路给谁」，而今天两条路径靠同一条规则就说得清。
