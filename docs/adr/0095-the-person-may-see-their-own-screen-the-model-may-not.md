# ADR-095：人可以看自己的屏幕，模型不可以——而今天一次被拒的点击就能把它读出来

- 决策点：computer use 的界面此前只讲规则、读不到任何状态，`ComputerPage` 的
  docblock 把这件事写成了有意的克制。要做一块能读到「这次批准了哪些应用、此刻前台是
  谁、最近的动作各过了哪几道门禁」的面板，第一个要回答的不是工程问题：**面板可不可以
  说出一个没被批准的前台应用的名字。** 代码里三处用同一条理由拒绝点名，而那条理由防的
  是模型；面板给的是人。这个区别今天一行都没写下来
- 状态：**接受**，并且是两个方向相反的决定：
  1. **人这一侧放开**：面板说出前台应用的名字，不论它有没有被批准。这是使用者
     2026-08-29 明确要的，而下面 §2 说明为什么它和现有的拒绝理由不矛盾。
  2. **模型这一侧收紧**：`ScreenGate._require_frontmost` 此前在拒绝里**点了名**，
     使「不点名」这条规则三处只成立两处。本 ADR 把它补齐——见 §3，这是一次
     **收窄**，且它是本 ADR 里唯一改变既有行为的一处。

  **明确不做**：不把 grant 从进程级挪到 MCP 会话级（F-19 保持开着，但措辞收窄，§4）；
  不给 computer MCP 服务器加 CORS（§5）；不持久化任何东西（§6）
- 日期：2026-08-29
- 影响：本 ADR 只写决定，落地分三步走，各自的影响在各自的提交里。
  §3 的收窄改 `apps/computer_mcp/gate.py` 与 `tests/apps/test_computer_gate.py`
- 依赖：[ADR-070](./0070-a-permission-is-about-a-window-not-an-application.md)
  （四道检查、会话级 allowlist、以及**拒绝持久化**——§6 依据的是它）、
  [ADR-091](./0091-choosing-a-window-is-choosing-within-a-set-somebody-approved.md) §2.2
  （「前台不在名单里就拒绝激活」，以及那条拒绝**不点名**的论证——本 ADR §3 补齐的正是
  它没有覆盖到的第三条路）、
  [ADR-092](./0092-a-server-that-changes-the-front-of-the-screen-is-an-application.md)
  （服务器是一个签名的 `.app`，主线程属于 AppKit——§5 的传输方案不能把服务挪回主线程）、
  [ADR-044](./0044-no-remote-no-production-identity.md)
  （agent-api 只信请求头、只绑回环——§5 让它成为一个只读客户端，依据的是它的这两条性质）

## 1. 缺口：一条被说了三遍、只成立两遍的规则

「不说出一个没被批准的前台应用叫什么」这条，在代码里出现三次：

| 位置 | 场景 | 点名吗 |
| --- | --- | --- |
| `domain/computer.py::activation_would_take_the_screen` | 模型要激活别的窗口，而此刻前台没被批准 | **不点名**，有测试钉着 |
| `gate.py::frontmost_grant` | 读工具问「名单里有没有一个在前台」 | **不区分**「有个没批准的」和「什么都没有」 |
| `gate.py::_require_frontmost` | 模型要在前台上点/打字/滚，而前台没被批准 | **点名** |

第三行是本 ADR 的起点。实测（2026-08-29，`FakeScreen`，已批准 Notes，人切到 Mail）：

```
[点击被拒]  "Mail" is not in this session's approved list, and the frontmost
            application is what left_click would reach.
[激活被拒]  "Notes" was not brought to the front: the application that is
            frontmost right now is not in this session's approved list.
[读名单]    frontmost_grant() → None
```

而 `activation_would_take_the_screen` 的注释把不点名的理由写得很清楚：

> naming it would turn every refused activation into a reading of what the
> person is doing -- which is the thing the allowlist exists to prevent, and
> **a strictly larger capability than the one being refused**.

那个「严格更大的能力」今天可以白拿：一次注定被拒的 `left_click(0, 0)` 就把它读出来了，
而且比激活更便宜——激活至少要先有一个被批准的目标，点击连目标都不需要。

**这不是有人写错了一行，是一条规则只在被单独论证过的地方成立。** ADR-091 §2.2 论证的是
激活那一条，落地时把不点名做进了那一条的文案；而 `_require_frontmost` 的文案早于它，
没有人回头看第三条路。测试的分布也印证：激活那条有 `assert "Mail" not in message`，
点击那条只断言「那句话在」。

## 2. 人这一侧：面板说出名字，而这不推翻上面那条理由

上面那条理由从头到尾说的是**模型**：allowlist 挡的是「一个不在这次任务里的窗口被一个
程序读到」。面板的读者是**坐在这台机器前面的那个人**，而那扇窗就在他自己的屏幕上——
他不需要这块面板也看得见它。

所以两件事的信息增量完全不同：

- 告诉模型 → 它得到了一个它无法自己获得的读数，而那正是 allowlist 存在的目的。
- 告诉人 → 它把这个人**已经看得见**的东西，摆在「所以你的任务停住了」旁边。

而后者是有用的：一个任务停在「前台不在名单里」上时，人要做的判断是「我要不要把我正在
用的这个也批准进来」。一块只肯说「不在名单里的某个应用」的面板，把这个判断变成了一次
猜谜。

**这条界限要能被检验，而不只是被声明。** 它的可检验形式是：那个名字只走人这一侧的读
路径，不进任何模型读得到的地方——不进拒绝文案、不进 MCP 工具的返回、不进事件流。§3 补
的正是这条界限上唯一还漏着的口子。

## 3. 模型这一侧：把第三条路补齐

`_require_frontmost` 在「前台不在名单里」这一支不再点名，改成和激活那条同一个口径：
说清是什么状况、说清补救是什么，不说那扇窗是谁。

**只改这一支。** 同一个方法的另一支——前台**在**名单里、但这一档 tier 不允许这个动作
——照旧点名（`refusal(action, application, tier)`），而且必须点名：那个应用是这个人亲手
批准进来的，说出它的名字没有泄露任何他没同意过的东西，而不说反而会让「终端不能打字」
这条拒绝变得无法排查。

**这会不会让拒绝变得不可用？** 不会，因为补救没变：等人切回一个被批准的窗口，或者请人
把当前这个也批准进来。名字不改变模型该做的下一件事——这也正是它可以被拿掉的原因。

这一处是本 ADR 唯一改变既有行为的地方，配一条断言名字**不出现**的回归测试，形状照抄
激活那条已有的。

## 4. 「这次会话」这三个字：F-19 保持开着，但措辞要收窄

`ScreenGate` 的 `_granted` 活在 **computer MCP 服务器进程**里：`create_server` 建一次
gate，被 `call_tool` 闭包捕获，`create_app` 只调一次 `create_server`。协议层确实有 MCP
会话（`stateless_http=False`），但 gate 不区分它们——这就是 F-19 记的那件事。

所以一块写着「**这次会话**批准了哪些应用」的面板是在说一句假话，它其实是「**这个进程**
批准了哪些应用」。

本 ADR **不修** F-19：把 grant 挂到 MCP 会话上要改 `create_server` 的形状（从「一个
gate」变成「按会话取 gate」），那是它自己的一批，而且它会改变现有客户端的行为。本 ADR
只做一件事——**让面板说进程**，并把 F-19 的条目措辞从「批准是进程级的」收窄成「批准是
进程级的，而界面上说的也是进程」。

这不是绕开缺口，是不让缺口再长出第二个：一块说「会话」的面板会让下一个人以为会话级
grant 已经有了。

## 5. 从 8768 到浏览器：agent-api 反代，不给 MCP 服务器加 CORS

这一节推翻了我自己先前的倾向，所以两个方案都写下来。

**方案 A：浏览器直连 `127.0.0.1:8768`。** 要给那个进程加 CORS。它的 `main.py` 开头写着
「Loopback only … 一个监听别处的端口就是一台远程输入设备」，而 CORS 不改变它监听在哪，
改变的是**哪些网页可以读它的响应**。`Access-Control-Allow-Origin: *` 意味着这个人打开的
**任何一个网站**都能读出他批准了什么、此刻在用什么——这不是理论上的，那正是 CORS 存在
的语义。收窄成一张来源白名单可以做，但控制台的来源是变的（`--web-dir` 挂在 8000、vite
开发服务器在 5173、别的端口另说），于是它变成一项必须配对、配错就是把屏幕状态交给任意
网站的配置。

**方案 B（采纳）：agent-api 加一条只读路由，转发到 8768。** 浏览器只跟控制台的同源后端
说话，同源策略原样生效，一行 CORS 都不需要，也就没有配错的那一档。代价是概念上的：
**控制平面成了一个能移动光标的进程的客户端**。这一条要正面接住——

- 它是**只读的一条路由**，转发的是那个服务器的只读出口，永远不转发任何动作工具。
  这条要做成可失败的测试，而不是一句约定。
- ADR-070 §1 说「agent-api 没有屏幕」，这句话仍然成立：它没有 `ScreenPort`，它拿到的是
  另一个进程算好的一段 JSON。它没有因此获得任何合成输入的能力。
- ADR-044 说 agent-api 只信请求头、只绑回环。这条路由不比它旁边任何一条更宽。

选 B 的决定性理由不是它更优雅，是**它没有一个「配错就把人的屏幕交出去」的失败模式**。
A 的安全性取决于一项配置写对，B 的安全性取决于浏览器的同源策略——后者不需要谁记得。

服务器那一侧新增的是一条 `GET /session`，挂在 `create_app` 里 `/health` 已经在的那个
位置。它是这个进程的**第一条披露性路由**：`/health` 只说这台机器有几块屏，这一条说的是
某个人批准了什么、此刻在用什么。所以它和 `/health` 不同——但它的读者经由 B 只能是同源的
控制台。

## 6. 最近的动作：有界的内存环，不落盘

「最近的动作各过了哪几道门禁」今天**一条数据都没有**：整个 `computer_mcp` 包零日志、
零事件，动作成功返回 `Grant`、失败抛 `ScreenRefusedError`，两条路都不记录。

所以要新加一个记录点，而它的形状被 ADR-070 已经定过一半：

> 把批准做成持久化的。会话级、进程重启即清空。一个跨重启记住「可以点这个应用」的授权，
> 是一个没有人再看着屏幕时依然成立的授权。

**一份跨重启的动作日志是同一类东西换个名字**：它记的是这个人在什么时候用了哪些窗口。
所以它和 grant 同寿命——`ScreenGate` 上一个有界的内存环，进程一关就没了，不写文件、不进
事件流、不进任何数据库。

有界而不是无界，理由是它挂在一个长命进程上：一个没有上限的动作列表，在一台开着一天的
机器上是一个只增不减的、记着这个人一天用过什么的结构。

## 7. 落地顺序，以及每一步各自能验到什么

| 步 | 内容 | 验到什么 |
| --- | --- | --- |
| 1 | 本 ADR + §3 的收窄 | 三条路口径一致，回归测试钉住名字不出现 |
| 2 | `ScreenGate` 的动作环 + `GET /session` | 单元测试；`curl` 那个进程读得到 |
| 3 | agent-api 的只读转发 | 架构测试钉住它只转发只读出口；控制台读得到 |
| 4 | `ComputerPage` 从说明页变成说明页 + 面板 | 浏览器实测，且「服务器没在跑」和「没有任何应用被批准」显示成两件事 |

第 4 步有一条不能省的状态：**这个服务器默认不启动**，所以「读不到」是常态而不是故障。
它必须和「读到了，名单是空的」显示成两件不同的东西——否则又回到了当初拒绝画假名单的那
个问题上。

## 8. 被拒绝的方案

**面板也不点名，和模型一样。** 那会让面板在最需要它的那一刻沉默：任务停住的原因恰恰是
「前台是某个没被批准的窗口」，而人要做的判断需要知道那是哪一个。而且它保护不了任何东西
——那扇窗就在这个人自己的屏幕上。

**保持 `_require_frontmost` 点名，只在面板这一侧做文章。** 那等于承认「不点名」只是一句
装饰。要么这条规则对模型成立，要么就把另外两处的论证一并撤掉；三处不一致是唯一不能留的
状态。

**把动作记录做成 durable 事件，进事件流。** 那是持久化，ADR-070 拒绝过同一类东西；而且
事件流是模型读得到的地方，会把 §2 刚划的那条线立刻抹掉。

**给 8768 加 CORS，白名单控制台来源。** 见 §5：可以做对，但它的失败模式是「配错就把屏幕
状态交给任意网站」，而反代没有这一档。
