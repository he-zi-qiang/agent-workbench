# ADR-047：会话的名字来自第一句话，而且只来自第一句

- 决策点：一个编码会话的名字由谁产生、在哪一层产生；「第一句指令」和「人工改名」
  谁能覆盖谁；这份列表放在浏览器还是服务端
- 状态：**接受**；关闭 `docs/known-gaps.md` F-06 的 Code 那一半，收窄 Chat 那一半
- 日期：2026-08-15
- 影响：`ConversationStore` 新增 `list_sessions` / `set_title_if_unset` /
  `rename_session`；`ConversationSession` 新增 `last_activity_at`；
  migration `0028_session_last_activity`；`GET /v1/code/sessions` 与
  `PATCH /v1/code/sessions/{id}`；`CreateSessionResponse` 回带 `title`；
  删除 `web/src/features/code/storage.ts`
- 依赖：ADR-028（工作区）、ADR-053（会话属于一个 API）——**这个号只被预留，没有写下**：
  它在 0047–0059 那批一次性分配的号段里（见 [ADR 索引](./README.md)「号段预留」一节）。
  此处记的是那条约束本身，不是一份读得到的文档；原先这里挂着一个指向
  `0053-a-session-belongs-to-one-api.md` 的链接，而那个文件从未存在过。

## 1. 背景：这份列表原来只在浏览器里

`title` 这一列从 migration `0001` 起就存在，`create_session` 一直接受它，Chat 也一直
在发送它——发的是第一个问题的前 200 字。但没有任何路由把它读回来过，Chat 自己在
localStorage 里另存一份，从不看服务端那份。Code 上一轮加的会话列表照抄了这个形状。

于是「找不回昨天那个会话」这件事的真相是：会话还在、还属于你、工作区版本也还在库里，
只是**唯一能进去的那把钥匙存在浏览器里**。清掉存储、换台机器，钥匙就没了。

## 2. 决策

### 2.1 名字在服务端产生，位置是 `_run` 里存下第一条用户消息之后

四条理由，按分量排：

1. **一个编码会话是在任何指令存在之前被创建的。** 控制台的「新建编码会话」按钮
   `POST /sessions` 时手上什么都没有。Chat 能在创建时命名（`ChatPage.tsx` 把问题
   截断当 title 一起发过去），Code 物理上做不到——它的创建和它的第一句话是两个请求。
2. **客户端方案只能是「第一轮成功后改名」，而它丢失时丢的正是那一个。** 关标签页、
   掉线、fetch 失败，任何一种都会留下一个无名会话——而无名的会话正是找不回的那个。
   这条失败恰好是这件事要消除的东西。
3. **`UPDATE … WHERE title IS NULL` 天然无竞态、可重试。** 第一条指令赢，重试写不进，
   人工改的名字永不被后来的指令覆盖。这三件事客户端一件也保证不了。
4. 用 curl 开的会话、将来任何非浏览器客户端，都白拿一个名字。

推导本身是 `application/session_titles.py` 里的纯函数：取第一非空行、合并空白、
按字符截断。空结果返回 `None` 而不是空串——`instruction` 的 `min_length=1` 允许
单个空格，而一个纯空白的标题会存进去、渲染成一行没人敢点的空白。

### 2.2 两个写方法，不是一个带开关的

`set_title_if_unset` **毁不掉**人打的字；`rename_session` 存在的意义就是毁掉。
一个 `overwrite: bool = False` 会把这两种含义塞进同一个调用点，而那个调用点写错
一次就是静默覆盖别人取的名字。

条件在语句里而不是在调用方。应用层那个 `if session.title is None` 只决定「要不要
费这个事」，仲裁者是 SQL 里的 `WHERE`。两层都在，而且**测试证明了两层都在起作用**：
只拆掉应用层那道，行为不变（store 仍然拒绝）；两道一起拆，测试才变红。

### 2.3 列表按「最后说话时间」排，而且那个时间戳写在 `_append_messages`

按创建时间排会把一个月没碰过的会话放在五分钟前刚聊完的上面——对一个唯一职责是
「把人送回他刚才在的地方」的列表来说，正好是反的。

时间戳的更新放在 `_append_messages` 这条缝上，因为那是每一次消息写入都经过的地方
（`append`、`claim_turn`、`mark_released` 都过它）。放进公开的 `append` 里，列表就
会按「哪个路由碰巧被调用」重排，而不是按「有人真的说了话」。PostgreSQL 里它跑在
已经持有该会话行锁的事务内，多一条 UPDATE、不多一把锁。

列名是新的而不是复用 `created_at`，NOT NULL 而不是可空：可空就得在排序里写
`COALESCE`，而 `COALESCE` 过的表达式用不上为这条查询建的索引。

### 2.4 `mode` 在 `list_sessions` 上必填、无默认

这个 port 上每一个读操作都把 mode 当门（见 `history` 的 docstring 和 ADR-053）。
列表是唯一一个「我拥有的全部」会直接穿门而过的地方：Chat 和 Code 共用一张表，
一个默认值会让某一天某个调用方拿到另一条流水线的会话标题。

### 2.5 用 `limit`，不用游标

`/v1/tasks` 分页，因为一个租户的 Task 无界增长。这是一个人最近的编码会话——在一份
由人类记忆定上界的列表上做 keyset 分页，是没有读者的机器。

### 2.6 标题是用户文本的截断副本

因此它继承对话的机密性：只返回给它的主人，走和 `history` 一模一样的三轴拒绝
（租户、principal、mode）。这不是额外的谨慎，这只是承认标题**是**对话内容，
而不是关于对话的元数据。

## 3. 后果

- **F-06 的 Code 那一半关闭。** 清掉浏览器存储、换一台机器，列表还在。
- **Chat 那一半没关。** 它的侧栏条目还带 `answerMode` 和 `knowledgeBaseId`，服务端
  不建模这两样。把 Chat 切到服务端列表是一个合并问题而不是接线问题，做一半会得到
  两份互相矛盾的列表。这条重新写进 known-gaps，而不是悄悄留着。
- **删掉了 `web/src/features/code/storage.ts`**，上一轮刚加的过渡方案。留着会让控制台
  对同一个问题有两个答案，而两个答案里总有一个是旧的。
- **代价**：`_append_messages` 在 Chat 回合的热路径上，现在多一条 UPDATE。它在已经
  持锁的事务内，但这是一句要被实测支持而不是被相信的话。

## 4. 什么会让这条决定重来

**会话开始有名字以外的元数据要展示的那天。** 消息数、工作区大小、最后一次跑的状态
——任何一个都会让「列表行是什么」从一次查询变成每行一次查询，那时该做的是一张投影
表，而不是给这个端点加 N 个可选字段。

**Chat 也搬到服务端列表的那天。** 那需要先决定 `answerMode` 和 `knowledgeBaseId`
属不属于会话本身。如果属于，它们该进这张表，而这份 ADR 的 §2.6 要重新问一遍：一个
知识库 id 是不是也继承对话的机密性。
