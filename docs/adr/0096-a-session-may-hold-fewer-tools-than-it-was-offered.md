# ADR-096：一段会话可以只拿它被给出的工具里的一部分

- 决策点：Claude Desktop 的输入框上有一颗「+」，菜单里可以逐个开关连接器与工具，
  于是「这一句话会让 agent 摸到什么」是发送**之前**就看得见、也改得动的一件事。
  这个控制台上看不见也改不动：一个 Code 回合拿到哪些工具，由
  `application/code_session.py` 里两条写死的元组、加上三个部署开关
  （`sandbox_enabled` / `host_commands_enabled` / `web_search_enabled`）决定，而
  `apps/api` 下没有任何路由说得出结果。要不要把它投影成 HTTP 事实；如果要，人能不能
  据此**收窄**下一个回合；以及这条收窄和已经存在的两条（计划模式、写入前批准）
  怎么排序
- 状态：**接受**。新增 `GET /v1/code/sessions/{session_id}/tools`，答的是**下一个
  回合**会被给出什么（§2）；`POST .../messages` 新增可选的 `tools`，语义是**保留
  哪些**，实现是与 offer 求交（§3）；`AskResponse` 新增 `allowed_tools`，答「我勾的
  那些到底生效了没有」（§4）。
  **明确不做**：不投影 `[[mcp.servers]]` 的连接器目录（§5）、不接受任何加宽
  （§3）、不让这条路由依赖 `mode` / `approvals` 两个查询参数（§6）、不给
  Chat 与 Task 做同一件事（§7）
- 日期：2026-08-30
- 影响：`application/code_session.py` 新增 `kept()`、`CodeToolOffer`、
  `CodeSessionService._offered()` / `offer()` / `unregistered()`，
  `CodeRequest` 新增 `tools`，`CodeTurn` 新增 `allowed_tools`；
  `apps/api/routes/code.py` 新增 `CodeToolView` / `CodeToolsResponse` 与
  `GET /sessions/{session_id}/tools`，`AskRequest` 新增 `tools`，
  `AskResponse` 新增 `allowed_tools`；
  `web/src/api/types.ts`、`web/src/api/client.ts` 各新增两项；
  `web/src/components/Menu.tsx`、`web/src/features/code/ComposerMenu.tsx`、
  `web/src/features/code/SessionMenu.tsx` 新增；
  `tests/application/test_code_session.py` +6 例、`tests/api/test_code_api.py` +6 例
  （**都不需要 DSN，进 CI**）。
  **不动配置契约**：没有新增任何配置叶子，`config_schema_version` 保持 `1.19`
- 依赖：[ADR-073](./0073-a-run-has-one-file-language.md)
  （offer 里唯一一件关于**这段会话**而不是关于进程的事，就是它说哪一种文件语言）、
  [ADR-079](./0079-a-plan-is-not-an-authorization.md)
  （第一条收窄轴，以及「只能变窄」这条性质该怎么写才检查得了）、
  [ADR-087](./0087-a-session-may-be-stricter-than-its-deployment.md)
  （第二条收窄轴；本 ADR 的标题是它那句话在第三条轴上的重复）、
  [ADR-093](./0093-a-console-may-read-what-the-next-task-would-be-allowed.md)
  （「只答下一个、不答已经存在的那个」这条线；本 ADR 是它在 Code 一侧的第二次划分）

## 1. 缺口：屏幕上没有一处说得出这一句话会摸到什么

一个 Code 回合被给出的工具，是三处事实的乘积：

| 来源 | 值 |
| --- | --- |
| 这段会话的项目有没有登记目录 | `CODE_TOOLS`（5 个）或 `CODE_PROJECT_TOOLS`（5 个，**不相交**） |
| `code.sandbox_enabled` / `code.host_commands_enabled` | `+ sandbox_run` 或 `+ project_run` |
| `code.web_search_enabled` | `+ web_search` |
| `multi_agent.delegation_enabled`（ADR-089） | `+ delegate` |

四行里没有一行是浏览器读得到的。第一行连服务端自己都要问一次
`ProjectService.open_files` 才知道——一段归到了某个项目、而那个项目没有登记根目录
的会话，跑的是**扁平工作区**，和它的归属看起来说的不是同一件事。

后果不是「少一个高级设置」。它是：读者按下发送之前，无法回答「这一轮会不会动我磁盘上
的文件」。ADR-077 已经为 `project_run` 单独立了一条「命令在跑之前先给人看」，而那条
规矩管的是**已经提议了的那一次调用**；在它之前，人对这个回合的能力范围一无所知。

## 2. 决定：答「下一个回合」，不答任何一个已经跑过的回合

这条线是 ADR-093 §2 的原话，在 Code 一侧第二次划：

- **输入框旁边的菜单**要的是这个进程此刻的能力，加上这段会话此刻的形状。它描述的是
  一个**还不存在**的回合，而那个回合一旦提交，拿到的就是这一份。
- **转录里的某一个回合**要的是它自己签过的那份信封。把今天的 offer 摆在三天前那一轮
  旁边，是在报一个它从来没有持有过的集合。

第二件事本 ADR **也答了**，但用的是另一个字段、放在另一个响应里：
`AskResponse.allowed_tools`（§4）。两个数长得一模一样而含义相反，所以它们连
出现的位置都不共用——路由的 docstring、响应模型的 docstring、前端 `types.ts` 的注释
三处都写了这句话，因为这是一个**读的人不会主动怀疑**的错误。

### 2.1 offer 由回合自己那条表达式产生

`_offered()` 是一个方法，而不是 `_run` 里的三行。这是本 ADR 唯一一处「为了未来的
读者而重构」的改动，理由不是整洁：

> 控制台读到的那份清单，如果是这段逻辑的**一份拷贝**，那么它和真正跑的那一轮只会
> 在有人改动其中一半之前保持一致。

测试把这一点钉成了断言 `tuple(offer.specs 的名字) == tuple(下一轮 signed.tool_names)`，
断言的是**同一条推导**而不是某五个名字——对着字面清单写的断言，会在有人编辑任何一半
之后继续通过。

### 2.2 offer 里的每一项都带着它自己的 `ToolSpec`

响应里给的是 `name` / `description` / `risk` / `kept_in_plan`，其中前三个直接来自
`ToolSpec`：

- `description` 是**模型读到的那一句**，不是为人另写的一句更友好的话。两套措辞会让
  「它为什么不用那个 grep」变成一个必须先 diff 才回答得了的问题，而其中只有一份是
  那个工具。
- `risk` 是审批闸门和计划模式**都在读**的那个字段。让调用方自己按名字前缀猜风险，
  等于把一个工具的风险写在第二个地方，而那正是 ADR-079 把计划模式从「按名字后缀过滤」
  改成「按 risk 过滤」时删掉的东西。
- `kept_in_plan` 是**调用** `read_only()` 算出来的，不是在路由里重写一遍
  `risk == "read"`。这条规则已经搬过一次家；没跟着搬的那份拷贝，会继续在一个计划
  回合不再持有的工具旁边画一个勾。

一个被 offer、但这个进程没有 spec 的名字，`offer()` 会**抛**而不是丢掉或者默认。
两种沉默各错各的：丢掉是给人看一份比真实回合更短的清单，默认是给人看一个没人声明过
的风险。`code_risk_ceiling` 早就用同一句话拒绝了同一种情况——本 ADR 只是把它的只读
一半也补上，于是一个「第一轮就会失败」的部署，改成在**第一次读目录时**就失败，而那
次请求发生在任何人花掉一次模型调用之前。

## 3. 决定：`tools` 只能减，减法是求交

`AskRequest.tools` 的语义写在函数名里：`kept(tool_names, keeping=...)`——**在 offer
的顺序里做交集**。于是：

1. 没有任何一种 `tools` 的写法能加进一个 offer 里没有的工具。这是把它暴露给浏览器
   的全部前提：请求可以被随便改，改出来的信封不会比这个部署已经决定发出去的那一份更宽。
2. 顺序是 offer 的顺序，所以「只会变窄」这句话仍然是**读两份清单就能验的**，而不是
   要信任某个函数。ADR-079 给计划模式立的正是这条形状，本 ADR 沿用它，于是两条轴复合
   起来不需要额外的论证：子序列的子序列还是子序列。
3. 顺序是**先 `mode` 后 `tools`**，而这个顺序是有内容的。计划模式是部署对「这一类
   回合可以持有什么」的规定；勾选是人在**剩下的东西里**表达的偏好。反过来排，一个
   勾选就没法让计划回合比计划模式本身更窄——它会去和一个还含着写入工具的集合求交——
   而那个在计划模式里取消勾选 `project_read` 的读者，会被正确地、但毫无用处地告知
   「什么都没变」。

### 3.1 两种「名字对不上」，两种处理

这是本 ADR 里最容易做成一件事、而它其实是两件的地方。

**不在这一轮的 offer 里** —— 丢掉，不报错。这是**常态**而不是客户端的毛病：控制台在
`act` 档读的目录，读者随后把控件拨到了「计划」，于是那份勾选里还留着 `project_write`。
在这里报错，等于把两个控件的一个合法组合变成一个错误。

**这个进程根本没有这个工具** —— 422，并且**把名字回给调用方**。这是打字错误或者一个
过期的客户端，而在这里沉默，就是「我勾了的那个工具没跑，而屏幕上任何地方都没有说
为什么」。这条拒绝发生在 `run_id` 被铸出来之前，所以一个搞错了的客户端不会因此花掉
一次模型调用。

`unregistered()` 一次返回**全部**对不上的名字而不是第一个：一个拿着过期目录的调用方
通常一次错好几个，而「一次一个来回地被告知」是那种最后没有人再修的错误形状。

### 3.2 空数组被拒绝，而不是被读成「全部」

`tools: []` 和不带这个字段不是同一个请求，这个差别值一个错误而不是一次猜测。

一个手里一个工具都没有的编码回合，读不了它正在讨论的那个项目，于是只能凭对话作答
——那是 Chat 的形状，不是这里的。而空数组同时也正是一个**自己的勾选状态还没加载完**
的客户端会发出来的东西：把它读成「全部」是一次没有人要求过的加宽，读成「一个都没有」
则是拿一次模型调用去换一个什么都做不了的回合。所以 `min_length=1`——真心想要空集的
调用方，代价是省掉这个字段。

## 4. `allowed_tools`：唯一能回答「我勾的那些生效了没有」的地方

三次收窄里有两次不是调用方做的：部署自己的 offer，以及这段会话的项目**有没有登记
目录**。所以「我发了四个名字，跑了两个」是一个正常结果而不是 bug，而这个响应里其他
任何字段都报不出它。

它带的是**信封被签的那一条元组本身**，不是在返回处再推导一次。第二次推导会是三条
收窄轴复合的第二个地方，而有意思的 bug 永远是这一对不一致。

## 5. 为什么不投影「有哪些连接器」

这是本批最容易顺手做错的一件事，和 ADR-093 §3 错得一模一样，只是主语换了。

Claude Desktop 那颗「+」里的 Connectors 一栏，列的是 MCP 服务器。这个仓库有
`[[mcp.servers]]`，`config.demo-local.toml` 里配着 `word` 和 `web` 两台。于是一个
「诚实地从自己手里取数」的实现会把它们列出来——**而 Code 回合永远拿不到它们中的任何
一个**：MCP 绑定是在 **Task Worker** 里按 audience（`research` / `synthesis` /
`delegation`）装配的（`apps/task_worker/composition.py`），`apps/api` 的
`_code_registry()` 里一个都没有。

列出来不是少答，是答错，且错得像对的：人会去勾一个连接器，然后发现 agent 从来不用它。

三条路都被否掉了：

- **列 `[[mcp.servers]]`**：错的，理由如上。
- **列一份写死的「Code 支持的连接器」清单**：把「哪个进程装哪些绑定」这条规则复制成
  两份，其中一份没有人会跟着改。
- **给这条路由加一个空的 `connectors: []`**：另一种形状的假话——它读起来是「这台部署
  没有连接器」，而这台部署有两台，只是不在这一侧。

所以答案是**这个进程不是知道这件事的那个进程**，而这条路由只答它真的发得出去的东西：
`tools`。这里有一个顺带的好处，也是这个形状唯一站得住的理由——**如果哪天 MCP 绑定真的
进了 `_code_registry()`，它们会自己出现在这份清单里**，因为清单是从注入的元组推出来
的，不是从一张按来源写的表。那一天不需要改这条路由，也不需要改前端。

值得单独记一句的是：`sandbox_run` **本来就是**一个 MCP 工具——它经由
`connect_mcp_client()` 连到 `apps/sandbox_mcp`。所以「Code 拿不到 MCP」这句话是错的，
准确的说法是「Code 拿不到 `[[mcp.servers]]` 里声明的那些」。界面按这个口径写。

## 6. 为什么这条路由不吃 `mode` 与 `approvals`

两个都是坐在这份清单三英寸之外的控件，而读者会一边读一边来回拨它们。让答案依赖它们，
就是每拨一次一个来回，去重新收到一份客户端已经有足够信息自己算出来的集合。

所以响应给的是**没有收窄过的 offer**，外加客户端收窄它所需要的两件事：每个工具的
`kept_in_plan`，以及这台部署的 `approval_required_risks`。算术在客户端做。

这不构成一个安全面：真正的收窄在服务端**又做了一遍**，而且是同一条表达式做的。这条
路由是给人读的，从来不是授权的依据。

## 7. 为什么不给 Chat 和 Task 做同一件事

**Chat** 的工具面是 `(knowledge_search,)`——一个元素的集合上没有可以表达的选择。

**Task** 的工具面在**提交那一刻**冻进 `run_semantics_snapshot`（ADR-040），而
`TaskInput` 参与 `canonical_bytes` 与提交幂等指纹——给它加一个字段就是动幂等键的一半。
ADR-093 §5 已经把这段账算过一遍，结论没变：能做，不该顺手做。

## 8. 被拒绝的方案

**把选择做成会话级的设置，存在服务端。** 一段会话的工具面就成了一个有状态的东西，而
「这一轮跑在什么上」的答案就要去查一个可以被另一个标签页改掉的行。它是**每一轮**的
属性，所以它和 `mode`、`approvals` 一样，是请求体上的一个字段。前端记不记得上一次
勾了什么，是前端的事（`localStorage`，按 session id），而它每一轮都要重新说一遍。

**做成 `denied_tools` 而不是「保留哪些」。** `AuthorizationEnvelope` 上确实有
`denied_tools`，且拒绝优先于允许。但那个字段表达的是「这个部署明令禁止」，把一个人的
临时勾选写进去，会让「为什么这个工具没跑」有两个都对的答案。求交只有一个。

**在信封里留下「人勾掉了这些」的记录。** 有吸引力，因为事后审计会想知道。没做：
`allowed_tools` 已经是那条记录了——它记的是**实际生效的集合**，而一份「被勾掉的」清单
是从两个集合的差里推出来的第二份事实，会在 offer 变化之后开始撒谎。

**什么都不做，让前端按 profile 写死一份清单。** 这是本 ADR 之前的状态。它在
`config.local.toml` 上是对的，在这个仓库自己的两个 console profile 上都是错的——而
第一行「这段会话的项目有没有登记目录」根本不是 profile 说了算的。
