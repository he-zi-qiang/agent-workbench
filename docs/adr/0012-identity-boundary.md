# ADR-012：v1 的身份边界

- 决策点：D0 Identity Boundary（代码实施计划第 10 节，WP04 之前）
- 状态：**接受**
- 日期：2026-07-25

> 实现核验（2026-07-25）：**当前实现不满足本 ADR 的安全前提**。默认
> `deployment_scope = "local"` 但 `api.host = "0.0.0.0"`，开发用 Header
> Identity Resolver 因而可能被本机之外的调用者访问并伪造身份。本 ADR 仍记录
> 产品决策，但“只部署在本机”必须由代码校验后才成立。

## 背景

实施计划要求在检索工作包之前把这件事定下来：v1 到底是一个单用户本地演示，
还是要接入一个已认证的 Principal Adapter。之所以必须先定，是因为 WP04 的
检索要按 ACL 过滤候选，而 ACL 过滤的意义完全取决于 principal 从哪里来。

到 WP03 结束为止，已经存在的事实是：

- `PrincipalContext`（principal / tenant / scopes）在 PR-003 就冻结在领域层，
  与传输方式无关；
- 租户隔离在三层实现并有测试——仓储、应用服务、HTTP。跨租户读与"不存在"
  在状态码、响应体和错误文案上完全同形；
- 每一个仓储方法都显式接收 tenant，没有任何一处从环境推断它；
- 唯一存在的身份解析器读两个请求头，只能用于开发；
- `app.deployment_scope == "remote"` 时，API **在装配阶段拒绝启动**。

也就是说，**隔离规则已经做完了，缺的是认证**。这两件事经常被混为一谈，而它们
的失败模式完全不同：隔离错了会泄漏数据，认证错了会让任何人成为任何人。

## 决策

**v1 在领域层是多租户的，在部署层是单机的。**

具体地：

1. tenant 与 principal 保持一等公民，所有仓储、服务与路由继续显式携带它们；
2. v1 唯一的 Identity Adapter 是读请求头的开发用解析器；
3. `deployment_scope == "remote"` 时 API 拒绝装配，这一条由测试守住；
4. v1 **不**引入 OIDC / JWT 或任何真实身份提供方。

## 被否决的选项

**A. 把 v1 降为单用户演示，删掉租户概念。**

更简单，但会让 WP04 的 ACL 过滤变得无法验证——而"检索结果按权限过滤、
撤权后旧答案不再可用"恰恰是这个项目在 RAG 方向上最值得展示的部分。已经写好
的隔离测试也会被删掉，将来重新引入多租户时再重写一遍。用简化换掉的是这个项目
真正想证明的东西。

**B. 现在就接一个真实的 Identity Adapter。**

OIDC 不是一个决定，是一组决定：JWKS 缓存与轮换、时钟偏移容忍、令牌撤销、
受众与签发者校验。每一项都是能微妙出错的地方，而现在没有任何消费者在推动它。
它还需要自己的威胁模型——基线 13.1 目前完全没有覆盖令牌层面的攻击面。在没有
部署压力时把这些做一遍，多半会得到一个没人验证过的实现。

## 安全前提与当前偏差

原决策所依赖的安全前提是：开发用解析器只能随一个仅监听 loopback 的进程运行；
任何可被本机之外访问的部署都必须先实现真实身份提供方。

当前代码只拒绝名义上的 `deployment_scope == "remote"`，没有检查实际监听地址。
默认配置又是 `0.0.0.0`，所以“local”进程仍可监听所有网卡。仅靠 remote scope
拒绝装配，不能证明服务无法被意外暴露。

在完成以下修复前，本 API 只能用于受控本机开发，不能暴露到局域网或公网：

1. 默认 host 改为 loopback；
2. Header Identity Resolver 启用时强制 host 为 `127.0.0.1`、`::1`、
   `localhost` 或受控 Unix socket；
3. Settings 与进程装配层都校验该不变量；
4. 增加真实 socket 绑定及 `0.0.0.0`、`::`、局域网地址的失败测试。

## 后果

### 可以怎么说、不可以怎么说

- **可以**：租户隔离已实现，并在仓储、应用服务与 HTTP 三层有测试；跨租户访问
  与不存在不可区分。
- **不可以**：生产级多租户认证。能力表中的认证一栏保持 Planned，简历与 README
  同样不得升级这一项。
- **同样不可以**：声称当前开发身份边界可以安全暴露到本机之外，或声称配置已经
  从机制上阻止意外暴露。

`scopes` 目前由调用方在请求头里自述，因此它**不是权限来源**，只是一个形状占位，
好让真实解析器接进来时不必改动下游。任何依赖 scopes 做授权的代码都属于越界。

### 对代码的约束

- `PrincipalContext` 只能在身份解析边界构造。`tests/architecture/
  test_identity_boundary.py` 强制这一点：允许构造它的模块是一份显式清单，
  新增一处就要改这份清单，也就必须有人解释为什么。
- 请求体永远不得指定 owner 或 tenant。
- 未来的 Identity Adapter 必须输出 `PrincipalContext`；令牌、请求头、cookie
  等传输层材料不得越过 `apps/` 边界。

## 何时重新决策

出现下列任一情况时，本 ADR 需要被一份新的取代：

- 服务需要在单机之外可达；
- 出现第二个真实用户；
- 有任何功能需要把 `scopes` 当作真实的授权依据。
