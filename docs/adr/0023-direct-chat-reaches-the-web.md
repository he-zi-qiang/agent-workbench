# ADR-023：无接地作答只有一个实现，联网能力跟着它走

- 决策点：`direct` 形态能不能联网；"无证据作答"这件事由几份代码实现
- 状态：**接受**
- 日期：2026-08-08
- 影响：`UngroundedExecution` 增加可选的 web 字段；`RoutedExecution` 的四个 `web_*`
  字段合并为一个 `fallback`；`WEB_FALLBACK_SYSTEM_PROMPT` 拆出 `WEB_DIRECT_SYSTEM_PROMPT`。
  **配置 schema 不变**——本 ADR 没有新增任何配置项

## 背景

ADR-021 把 `web_search` 挂在 `routed` 的兜底分支上，论据是那条分支的触发条件
（"语料库没有覆盖这个问题"）恰好就是外部信息可能有用的时刻。这条论据是对的。

它漏掉的是：**系统里还有另一条"无证据作答"的路径，而且是控制台默认打开的那条。**

`AnswerModeSelector` 按请求里有没有知识库分流。没有 → `direct`（ADR-018 的
`UngroundedExecution`）。而 Chat 界面的资料选择器默认停在「不使用知识库 · 自由回答」。
于是实测下来是这样：

| 用户做的事 | 实际发生的 |
|---|---|
| 打开 Chat，问"丹东今天天气" | 模型凭记忆猜，它连今天是几号都不知道 |
| 先选一个和问题无关的知识库，再问同一句 | 检索、判定不相关、**联网搜到真实天气**并给出三个来源 |

也就是要求用户先挂一个他明知道没用的知识库、等它检索失败，才能拿到正确答案。
这不是一个可以在文档里解释清楚的行为。

## 问题

真正要回答的不是"要不要给 direct 加个工具"，而是 ADR-018 自己在末尾写下的那个条件：

> ## 重审条件
>
> 如果无接地路径开始需要工具、需要多轮记忆预算、或者有人要求它也给出引用，那说明它
> 正在长成第二个 Chat 实现。届时应当重新评估：**要么把它合回检索路径**，要么给它自己
> 的工作包，而不是继续在同一个 `TurnExecution` seam 下面加分支。

条件已经触发了，而且是从另一头触发的：不是 `UngroundedExecution` 长出了工具，是
`RoutedExecution` 里已经长出了一份**完整的无接地作答实现**——`_ungrounded_answer`、
`_answer_without_evidence`、四个 `web_*` 字段，加起来做的事和 `UngroundedExecution`
做的事是同一件。第二个实现已经存在了，只是长在了另一个类里面。

所以"给 direct 也加四个字段"是最不该选的那个选项：它会把两份实现变成三份。

## 决策

### 一、`UngroundedExecution` 是"无证据作答"的**唯一**实现

可选的 web 字段搬到它身上，`RoutedExecution` 的兜底分支改成**委托**给一个
`UngroundedExecution` 实例（字段 `fallback`）。ADR-018 给的两个选项里选"合回"。

这条同时把 ADR-021 §6（兜底永远交付一个回答）变成两条路径共有的性质，而不是
`routed` 独有的。那一节记录的失败——搜过网的回合因为 `budget_exceeded` 变成 HTTP 502，
**比没搜过的回合给用户的更少**——如果只是把工具复制给 direct，会原样复现一遍。

装配层因此也只建一份：一个 `web_tool`、一个 `WebSearchJournal`、一个 runtime，两条路径
共用。这不是省事，是必须——工具 binding 只往**一个** journal 里写裁决，建第二个会让持有
另一个的那条路径永远读到 `False`，也就是把"这回合读过网"记成"没读过"，而且什么都不会报错。

### 二、判断依据是"这个回合有没有证据"，不是"哪条代码路径"

ADR-021 §2 立的边界是：**语料库能回答的问题，永远从语料库回答**，否则 `routed` 就不可
测量了。本决定不碰这条——`routed` 的接地分支照旧完全够不到工具，兜底照旧只在
`RetrievalRejected` 之后才发生。

而 `direct` 根本不在这条边界的管辖范围内：**它没有语料库可以先问。** 用户选择「自由回答」
就是明确表示这一轮不查知识库，这和 `routed` 查过之后发现查不到，在"手里没有证据"这一点
上是同一个状态。工具跟着状态走，不跟着类名走。

ADR-018 那句"切换依据必须是授权后的证据，不能是问题本身"仍然没有被违反：这里没有任何
东西在**猜**该走哪条路。走哪条是用户在界面上选的，留在 `answer_mode` 里；走进来之后
搜不搜是模型的判断，留在 `ToolProposed` 事件里。两个决定都有据可查，这正是 ADR-021 §1
用来给"让模型自己决定"正名的那条理由。

### 三、两条路径的提示词**必须**是两句话

`WEB_FALLBACK_SYSTEM_PROMPT` 的第一句是"The knowledge base did not cover this
question."。把它原样给 direct，等于告诉模型一个**它从来没拿到过的知识库**没能覆盖这个
问题——在模型唯一真正会读的那个地方，陈述一次没有发生过的检索。

所以拆成共享的规则正文 `_WEB_TOOL_RULES` 加两句不同的开头。规则正文一字不差地共用，
因为装配层那个 `max_steps=3 / max_tool_calls=2` 的上限（ADR-021 §5、ADR-022）管的就是
"最多搜两次"这句话，两条路径共用同一句话才能共用同一个上限。

这条是 ADR-018 那个论点往下一层的应用：它花了一整节论证 `UngroundedAnswerCommitted`
不能复用 `AnswerCommitted`，理由是"一条读者无法区分来源的记录，比没有记录更糟"。
读者换成模型，记录换成提示词，结论不变。

### 四、读过网的 direct 回合，照旧**不算接地**

`grounded=False`、`citations=()`、`authorized_revisions=()`，走
`UngroundedAnswerCommitted`。这一条一个字都不改——ADR-021 §3 的论据（抓来的页面没有
revision、没有 ACL、没有任何发布门可以复核的东西）与这个回合是不是 direct 完全无关。

对 direct 而言这甚至不是新增约束：它本来就永不产生 `Citation`，本来就走
`UngroundedAnswerCommitted`。变的只是它现在**有能力**给出一个基于真实网页的回答，
而不是一个关于今天天气的幻觉。收回的仍然是保证，不是来源。

### 五、没配 provider，什么都不变

ADR-021 §4 原样适用，并且现在多一条测试钉着（`test_without_a_provider_the_direct_shape_gains_no_tool`）。
`research` 为 `None` → `web_executor is None` → `direct` 就是 ADR-018 那天的
`direct`：一次模型调用、deny-shaped 信封、无工具。一个什么都没配的部署不会因为本次
合并而开始花钱。

## 后果

- **计费面再次变大，而且这次是默认路径。** ADR-021 已经把 Chat 纳入了搜索计费，但那
  需要用户先选一个知识库；现在控制台默认模式下的任何一个问题都可能触发搜索。硬边界
  仍然是 scope（`external:search`）和信封，提示词里"算术、定义、能凭知识写出的代码
  ——不要搜"依旧只是提示词；

- **而且实测它确实不听。** 落地后立刻量了一次："用一句话解释什么是快速排序"——一个
  提示词点名不要搜的定义类问题——模型照样搜了两次，33 秒，答案里挂着百度百科的链接。
  这不是新问题（ADR-021 §5 记的就是"提示词不是预算"），但此前它只发生在用户主动选了
  知识库并且检索落空之后，现在它发生在默认路径上，也就是**每一个随口问的问题**。真正
  在约束成本的仍然只有 `max_steps=3 / max_tool_calls=2` 那个上限：贵的是每回合最多两次
  搜索，不是"模型会自觉判断"。如果这个成本不可接受，正确的下一步是备选方案里那个被
  推迟的手动开关，而不是把提示词写得更严厉；
- **`routed` 的可测量性不受影响**，这是刻意保留的：`tests/application/test_routed_chat.py`
  的 23 条断言在本次重构中**一条都没有改**，只改了接线。它们是这次合并的对照组；
- 本机上 direct 联网回合与 routed 兜底同样要 60–90 秒。此前 direct 是**唯一**秒回的
  模式，用户会感觉到它变慢了——变慢的是那些它以前答错的问题；
- ADR-018 的重审条件**就此消耗掉**。无接地路径现在确实有工具了，处理方式是它给的两个
  选项里的第一个。如果将来它还要多轮记忆预算或者要求引用，那是一个新的重审，不能再引用
  这一条当先例；
- `AnswerModeSelector` 的形状不变，`ChatRequest` 不变，HTTP 契约不变，配置 schema 不变。

## 备选方案

**给 `direct` 也加四个 `web_*` 字段。** 最小 diff，被否决：它把两份"无证据作答"实现变成
三份，而 ADR-018 的重审条件点名的就是这件事。第三份还会各自持有一个 journal，那个 bug
不会有任何东西报错。

**让 `routed` 在没有知识库时也接受请求（即取消 `_required_knowledge_base`）。** 被否决：
`routed` 的定义是"先检索再决定"，没有知识库时它就只是 `ungrounded` 换了个名字——这句话
是 ADR-018 原文写下的，本决定没有理由推翻它。

**在输入框加一个「联网」开关。** ADR-021 已经评估过并否决，理由是"那是你分辨，不是它
分辨"。这里再记一次是因为它作为**覆盖手段**仍然成立：自动判断加一个手动否决不冲突。
需要时另开 ADR，本决定不预先实现。

**把默认模式改成选中某个知识库。** 被否决：这是把一个后端能力缺口伪装成界面默认值，
而且会让每一个随口问的问题都付一次检索和重排的钱（本机 60 秒起）。

## 重审条件

如果出现"用户明确想查知识库、模型却去搜了网"的实测案例，说明第二节那条"工具跟着状态走"
的推理在真实分布上不成立，届时应重新评估是否需要把工具限制在显式开关之后。
